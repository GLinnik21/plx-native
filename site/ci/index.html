How long a pull request waits

Per commit, the longest job of its CI and Simulator CI runs, which is what a push waits for (the runs go side by side). The thin lines are each workflow's own longest job. Queueing before a job starts is not in GitHub's job timings, so real waits are a little longer.

    CI: every job

    One line per job that finished green, taken from the data as it comes: a job that is new starts a new line, a job that was removed ends its line, and a run without a job leaves a gap, not a zero.

    Simulator CI: every job

    The same, for the simulator workflow.

    Runner minutes per push

    The sum of every green job's minutes, which several optimisations traded wall time against: a split into parallel jobs lowers the wait and raises this. The total counts only commits that ran both workflows.

    Red pushes and re-runs, per week

    The share of finished CI and Simulator CI runs on main that failed, and that passed only after a re-run. Cancelled runs (a newer push superseding an older one) are not counted.

    Local development loop: measured milestones

    These are not collected: each number was measured by hand with make build-bench (or the timing the PR names) on one Apple M4, 10 cores, and quoted from the body of the merged PR that made the change. They are comparable with each other and not across machines, nor with the CI runners above. A bar pair is the same measurement before and after; a lighter extension is the upper end of a quoted range.

    Host checks ran as one job until Oct 1; since then they are parallel jobs plus a short aggregator, and the chart shows each separately. Runner timings on shared GitHub machines are noisy, so read the median line, not single dots. Numbered markers are pushes titled Build:, CI: or Check:.

    Pull-request runs are not collected, so the wait is the one of the push that merged the PR, which runs the same jobs. The nightly dry run (ARM build + gates) only runs on pull requests that touch its inputs and is not here. Red runs are recorded since the collector learned to (rows older than that read as green until a full refresh).

    The data is ci-history.json on the ci-metrics branch. Adding a milestone: append a point to site/ci/milestones.json (date, pr and commit, value in the series' unit, optional before and max, what, and a one-line source), or start a new series; take the number from a PR body, never estimate one.
