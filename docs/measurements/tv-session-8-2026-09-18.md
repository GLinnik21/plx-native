## Legs run and passed — player lane

Driven through the remote FIFO. The player logs exact markers, so these are graded on log text,
not on a judgement call.

**Paused scrub on the real pipeline — PASS.** Playback opened from a Continue Watching card and
ran on the real path:

```
route: dolby vision P8 (bl_compat=1 el=0) … direct play
acb setMediaAudioData rv=1 … "immersive":"ATMOS"
ff: seek … rv=0
rebase: first post-seek keyframe …
```

OK paused it (`timeline paused t=1655s/6160s`, heartbeat `play=0pm`), and every scrub below
committed **while paused** — the heartbeat stayed `play=0pm` across all of them, i.e. the commit
held the pause as designed.

**One tap = one `scrub: tap commit` — PASS.** With the HUD already up, a single `right` took the
marker count 2 → 3, and the committed target advanced exactly one 10 s step each time:
`scrub: tap commit 1675s`, `1684s`, `1693s`. No double-commit.

**The `SCRUB_LOST_MS` net — PASS.** `holddown:right` plus three `holdrep:right` and **no
release** produced `scrub: hold engaged (0x101 repeat)` then `scrub: lost keyup commit 1711s`. A
dropped keyup commits the ramp instead of stranding the gesture, on the real device.

Method note worth carrying into the next session: the HUD must be *visible at press* or the press
is spent revealing it (`input::scrub_press`). Each `tv-session.sh key` is its own ssh round trip
(~1 s), longer than the HUD linger, so tokens must be sent in ONE burst (`key right right`) or
every press is a Reveal and no `scrub:` marker ever appears. A right-tap with the HUD down seeks
directly (`ff: seek`) without touching the scrub path at all. This cost the first three attempts
this session; it belongs here so the next one does not re-derive it.

  press-move-move-release cannot be expressed. `remote_synth_pointer` can emit a single pointer
  event but is reachable only from the replay driver, not from the FIFO.
- **Pointer-motion HUD raise "feel" — NOT COVERED.** Two reasons, both real: the panel is off by

- **"App-switch parks the nav stack" — NOT COVERED.** Backgrounding via

## New findings (both found only because this ran on the device)

### A. On-screen identity names the account holder, not the signed-in managed user

Signed in on the managed test user's token, the profile chip renders the **account holder's**
name, and the account overlay header repeats it. The manifest's test-user title is a different
string (verified by comparison in-session; neither value printed here). So the one signal a human
uses to confirm "am I on the guest?" before touching playback names the wrong person.

This matters because of the 2026-09-10 postmortem that `--guest` exists for: a caller asked for a
guest, silently got the owner, and a real playback wrote progress into the household account. The
harness CLI refuses to fall through now, but the screen still cannot tell the two identities apart.

### B. As a managed user, "Change profile" is a dead end that only Sign out escapes

Account overlay → **Change profile** → `route=profiles`, "Who's watching?", a spinner and nothing
else. Root cause established: that token gets **401** from both `/api/v2/home/users` and
`/api/v2/user` (probed directly; only status codes recorded). A managed user cannot enumerate the
home roster through those endpoints.

What the app does with that: spins **forever** (still spinning after ~11 s), shows **no error**,
writes **nothing to the log** (no 401, no failure line — the silent-instrument trap), and **Back
does not leave** — three `back` presses, still `route=profiles`. The only control on screen is
"Sign out." A household guest who opens that menu loses their session with no way back short of
that.

Recovery in this session was a relaunch (`up --guest --screen home`), which a viewer cannot do.

This is the same shape as issue #75 (a failing sign-in that telemetry cannot see): the fix is an
on-screen failure surface plus a working Back, not a silent retry.
