# P3 — the specification's adversarial review

**Five seats, each attacked by an independent refuter.** Run 2026-08-27 against
`docs/adaptive-playback-spec.md` at commit `a2bca9e4`. Seats: evidence, numerics, control,
decision, implementer. Every refuter was told to default to *refuted* when uncertain and to
correct a finding that was directionally right but overstated, rather than wave it through.

**13 findings survived, 7 were killed.** This file is the record; the
corrections are applied in the specification itself.

The first attempt at this review returned `{confirmed: [], killed: []}` because all five seats
hit a usage limit mid-read — an empty result that reads exactly like a clean review. The
cause was the review script pointing every seat at 350 KB of reading before any thinking. It
is recorded here because *an empty pass is not a pass*, and the shape recurs.

## Survived

### [blocks-phase-4] §5 — §5's trigger set contains no upshift condition — climbing is unreachable
*seat: control*

**Claim attacked.** "Trigger — when to reconsider at all. ¬sustainable(current) under §4, or draining(). This was never written down anywhere." — together with "Target — which rung to move to. The highest rung that is sustainable ... a jump from 8 to a 15 Mbit/s budget primes the 14 Mbps encoder once", which presumes upshifts happen.

**Defect.** Both trigger predicates are distress conditions. From a healthy state — current rung sustainable, reserve flat — neither fires, so the target rule is never evaluated and the controller can never climb. §5 opens by blaming the plan for making "the emergency path look like the only path (R23)"; as written §5 makes it literally the only path.

**Evidence.** Spec §5 lines 219-224 define the trigger as exactly {¬sustainable(current), draining()}. The shipped controller has the missing third arm and it was added because of a device finding: rust-modules/src/abr/controller.rs:304-340 recomputes `best_sustainable(safe_budget*4/5)` on EVERY segment and primes an upshift on `DecisionReason::Hls(HlsReason::SafeBudgetIncrease)` when `target > current`, gated on `!draining` — and rust-modules/src/abr/plant.rs:160-167 records the symptom of losing exactly that arm: "measured on the television 2026-08-25 ... Auto sat on the 10 Mbps rung with a 25 Mbit/s safe budget and a full reserve for the rest of the film." §5 reintroduces that state by construction rather than by an EWMA artefact: it requires `draining()` to be TRUE before a climb can even be considered, where the old bug only required it to be spuriously true.

**Consequence.** Phase 4 implemented from §5 boots at the bootstrap rung and stays there for the whole film on any link that is comfortably fast, reproducing the exact 2026-08-25 device regression the shipped DRAIN_EPS work fixed. No unit or sim test keyed on distress traces would see it, because nothing distressing happens.

**Refuter's correction.** The defect is real but the consequence is conditional, not automatic. Correct statement: §5's trigger set (lines 219-224) contains only distress predicates, so as written the target rule is unreachable from a healthy state and the section fails its own stated purpose (R23). It does not follow that Phase 4 necessarily boots at the bootstrap rung and stays there — spec line 5-6 defers to the plan where the spec is silent, and plan N7 explicitly preserves the safe_budget-driven upshift proposal together with its reserve gate and `&& !draining`. The defect is therefore an unresolved ambiguity at the top of the control loop: §5 claims exhaustiveness ('when to reconsider at all', 'never written down anywhere') for a trigger set that omits the one arm the shipped controller has, and the spec's own conflict rule ('later on formulas', 'plan governs on silence') does not say which reading wins. Worth noting alongside it: R23 — and every other R-number §5 and §7 cite — resolves nowhere in the repository (`grep -rl R23` returns only the spec), so the reader cannot check what §5 claims to be correcting.


### [blocks-phase-4] §4 — Worst-case-only admission with no reserve term cannot upshift on a median-affordable link
*seat: control*

**Claim attacked.** "A rung is sustainable when one segment's acquisition fits inside the media it provides: A_j ≤ D", with `bytes_worst = σ·W_j·D/8000`, σ = 0.85 — i.e. every segment charged at the structural ceiling.

**Defect.** The rule is stateless in B: the reserve, which is the only physical reason a buffered player may run a rung whose PEAK exceeds the link, appears nowhere on the admission side (it appears only in §5's downshift deadline). Charging the ceiling per segment makes the admissible declared rate ≈ the link rate, while measured delivery at high rungs on easy content is 0.14–0.26 of declared, so the controller settles 3 ladder steps low and leaves ~2.8× of deliverable bitrate unused.

**Evidence.** Solving §4's shipped integer form with τ_ps = 8e12/C gives W_j ≤ C·(1 − O₀/D)/σ; at the measured O₀ = 214 ms (p2h §5) and D = 2000, that is W_j ≤ 1.05·C. On C = 6000 kbps: W_max = 6304 kbps, so rung 6000 (declared 5696) is admitted and rung 8000 (declared 7515) is refused. Recomputed from docs/measurements/p2h-logs/movie-opening-segments.csv (8·Σbytes/Σduration per rung): rung 6000 aggregate delivered = 1815 kbps — 30% of that link — while rung 22000's aggregate over the same 80 s window is 5080 kbps, which the 6 Mbit/s link carries. 5080/1815 = 2.80×. The single worst segment at rung 22000 is 16 682 kbps, i.e. 5.56 s of fetch for 2.0 s of media = 3.6 s of drain — inside the ≈5.4–6.9 s the queue geometry can hold at that rung (1600 + 8·8 MiB/R, sim.rs:200-213), but §4 has no B term to spend it from. Nuance that keeps the finding honest: on the harder movie/40min window rung 22000 aggregates 12 674 kbps, so the fix is not "raise σ", it is an admission rule with an aggregate-rate term and a reserve term.

**Consequence.** Auto never leaves the low ladder on ordinary easy content — visually the exact user-visible complaint the whole ABR effort exists to fix — and the spec's own §8 device work (O₀, τ, the A/D ∈ [0.80,1.05] band) cannot diagnose it, because the rule is behaving exactly as specified.

**Refuter's correction.** Two parts must be withdrawn. (1) 'Settles 3 ladder steps low' is unsupported by any recomputation: on the measured easy window the mean-affordable rung at C=6000 is the ladder TOP (5080 kbps aggregate at rung 22000, eight steps above 6000), and on the hard window it is rung 10000 (5860 kbps, two steps) — the gap is window-dependent and 'three steps' matches neither. (2) The 2.80× is not deliverable headroom being wasted; it is a bet on content, since the same film's 40-min window aggregates 12 674 kbps at rung 22000 against the same 6 Mbit/s link, so an admission rule that spent it would guarantee a collapse at the difficulty change. The surviving defect is narrower: §4 charges every segment at §3's content CEILING and carries no reserve term and no sustained-rate term, so admission collapses to 'declared ≲ 1.05 × link' on a ladder whose delivered/declared median moves 4.3× with content (p2h §2). That is the maximally conservative point on a real trade — never drain, at the price of never exploiting easy content, and of dropping the one-sided buffer-deficit term viability.rs:82-88 already has — and the specification presents it as a derivation from the physics rather than naming it as a choice with its trade, which is exactly what the classification rule forbids.


### [blocks-phase-4] §7 row risk_weight — Deleting risk_weight leaves an unavailable, non-commensurable term
*seat: decision*

**Claim attacked.** "**Delete.** Under §4 the risk term is a probability with units, not a score in `{1,4,12,40} + 20 + 30`. A weight exists only to make a score commensurable, and a probability already is."

**Defect.** A probability is dimensionless; the other three terms of the sum are in quality points, so a probability is precisely NOT commensurable with them — it needs a cost-of-stall coefficient in points, which is the weight being deleted. And no probability is produced anywhere in this specification, so the row deletes a live coefficient and substitutes an object that does not exist.

**Evidence.** mode.rs:164/215 compute `total = quality - risk_cost - server - transition` where `quality` is `hls_quality_score` ∈ [0,76] (mode.rs:126-136) plus `original_quality_bonus` 40 and `original_feature_bonus` 25 — max 76 (HLS) / 141 (Original). §6 mandates "integer i64 throughout, no floats" and "per-mille for dimensionless ratios", so a probability enters as 0..1000: any P ≥ 76 pm (7.6%) outweighs the entire HLS quality range and P ≥ 141 pm (14.1%) outweighs Original's, and the argmax degenerates to "minimise P". Expressed instead as a bare i64 in [0,1] it truncates to 0 for every P < 1 and the risk term vanishes. Availability: §4's admission rule is a deterministic inequality (`1_000_000*o0_us + bytes_worst*tau_ps <= 1_000_000_000*d_ms`), §3's σ=0.85 is a max over 1 120 segments not a distribution, p2h §4 refutes both AR(1) and exchangeability, and §8 bullet 4 states outright that "λ and `P(revert)` are not available at all (R6): four events, dispersion index 10.8, and a 95% CI of width 0.6." The plan's own ledger already named the real defect and it is not the weight's existence: §6.3(1) "Utility is invariant to a common scale, so only ratios matter… every weight lands with a written indifference statement… expressed as a ratio to `visible_switch_cost` as numeraire." Deleting risk_weight sets that ratio to 1 by omission instead of by an indifference statement.

**Consequence.** §7 row 17 and §8 bullet 4 contradict each other inside one document. Phase 4 cannot implement the mode comparison: whoever writes it must invent both the probability and the exchange rate the spec says are settled, and the two obvious unit choices break the argmax in opposite directions (risk dominates 13:1, or risk disappears).

**Refuter's correction.** §7's `risk_weight` row (spec:288) deletes the only coefficient converting `CandidateRisk::score` into utility points (mode.rs:157, mode.rs:206 — the sole non-test uses) and replaces it with a probability the specification never constructs. The document's only probabilistic apparatus is `production_safe_pm`'s own undone verdict at spec:272 ("the conformal quantile on `A`"), and even that would yield a per-segment exceedance probability, not a stall probability — converting one to the other requires the buffer-relaxation model §1 states is unavailable in closed form ("misses by up to 6 238 ms") and §8 lists as not done. §8:311 separately records that λ and `P(revert)` are unavailable (four events, dispersion index 10.8, 95% CI width 0.6). The row also leaves the functional form unstated: additively at unit weight under §6's per-mille rule a probability ≥ 76 pm outweighs the entire HLS quality range [0,76] (mode.rs:127-135) and ≥ 141 pm outweighs Original's 141 (40 bonus + 76 for P1080High + 25 features), while a multiplicative form `quality*(1000-P_pm)/1000` needs no coefficient at all and degenerates in neither direction. Phase 4 must be told which. Finally, the plan's own prescription for this weight is not deletion: plan:912-913 asks for an indifference statement expressed as a ratio to `visible_switch_cost` (plan:856, "it is the numeraire"); deleting the weight fixes that ratio at 1 by omission.

### [blocks-phase-4] §3 (Classification) and 5 (Target) — Candidate's declared W_j does not exist when §5 picks the target rung
*seat: implementer*

**Claim attacked.** "`W_j` is (2) directly measured, per transaction, from a playlist the transaction **already fetches and already logs** (`ff.rs`, `hls: master one-variant bandwidth=`)" — and §5's "Target … the highest rung that is sustainable under §4".

**Defect.** The transaction fetches exactly ONE master playlist per encoder session: the one it is already playing. A rung j's `BANDWIDTH` cannot be read without first creating a PMS encoder session for j, so at the moment the target is chosen no candidate's W_j exists. Worse, the number is not even retained for the rung that does have one — it is formatted into a log string and dropped.

**Evidence.** `ff.rs:2642` `hls_cursor_open` logs `master.variant.bandwidth` at `ff.rs:2660` and returns `HlsCursor` (`ff.rs:2623-2641`), whose eight fields contain no bandwidth — the value has no reader. The current session's master is opened once at `ff.rs:3209`. A candidate's master is opened at `ff.rs:3466`, AFTER `control.prime(…)` at `ff.rs:3446`, which builds a fresh `transcode_spec` under a new encoder-session id (`route.rs:424-455`) — a real PMS transcode session. The target rung is chosen upstream of all of that, at `controller.rs:304-305` `self.catalog.best_sustainable(safe_budget * 4 / 5, …)`, which iterates `HlsCandidate`s carrying only the catalog's `expected_wire_kbps`. `SegmentSample` (`estimate.rs:258-264`) and `candidate_ready` (`controller.rs:349-367`) have no field for a declared rate either, so even the post-prime value is unplumbed.

**Consequence.** §4's rule cannot be evaluated over the ladder at all. The implementer must either (a) substitute the catalog rate — which `p2h` §6 measures at +5.2 % to +31.6 % error, item-dependent (rung 720 declares 547 on one item and 425 on two others, a 29 % spread) and non-injective (18000 and 20000 both declare 16 150, 39/40 segments byte-identical) — i.e. reinstate exactly the input R1 killed; or (b) invent a speculative prime-per-rung probe that starts a server transcode session for every candidate examined. Neither is in the document.

**Refuter's correction.** Two overstatements to trim. (a) The dichotomy is false: a third option exists — memoise W_j from each rung as it is primed, or probe `/decision` per candidate (13-18 ms warm, p2h §5) — but neither reaches a rung never visited, which is exactly the target-selection case, so the defect stands. (b) The log line is at ff.rs:2661, not :2660 (p2h cites :2660 too). Sharpest statement of the defect: §3 classifies W_j as "directly measured, per transaction, from a playlist the transaction already fetches", which is true only of the rung whose encoder session already exists — the rung already playing, or a candidate already primed. §5's Target requires §4 evaluated over rungs that have neither, so admission and selection need the same quantity at two different times and only one of them can have it.


### [blocks-phase-4] §header ("whose estimation is specified"), 2, 4 — No estimator is specified for O₀ or τ, and O₀ is not a scalar
*seat: implementer*

**Claim attacked.** "§4 is therefore written with those two as named parameters whose *estimation* is specified and whose *values* are a device job."

**Defect.** Nothing in the document specifies an estimator for `o0_us` or `tau_ps` — no form, window, update law, cold-start value or bound. §2 says the opposite of the header for one of them outright. And §2's own measurements make O₀ a function of rung and of history, while §4's arithmetic takes a single scalar with no regime selector.

**Evidence.** §2: "`τ` … is not measurable on the host apparatus and is not specified here. The device tier owns it." — a direct contradiction of the header. §2's table gives three O₀ regimes (k·108 ms steady; ≈660 ms for exactly one segment after a seek; 862 ms median / 1 306 ms max at rungs ≥ 12000 on a hard source), i.e. O₀ varies with rung and with a seek that §4's `o0_us` cannot express. The shipped sample carries one acquisition number per segment — `total_fetch_us` and `active_fetch_us` (`estimate.rs:259-263`) — so splitting it into an intercept and a per-byte slope needs a stated procedure. Repo evidence that none exists: grep for `tau|o0_us|intercept|per_byte|ps_per` over all 4 463 lines of `rust-modules/src/abr/*.rs` returns zero hits. The seek regime is undetectable in this path: `on_seek` exists only on the Original estimator (`abr/original.rs:340`); the HLS controller has no seek hook.

**Consequence.** Phase 4 cannot be written from §4. Every one of the estimator's shape decisions — EWMA vs median, window length, per-rung vs global, what to do for the one post-seek segment, what value to use before the first sample — becomes an invented constant, which is the exact class of number the directive bans, sitting on a boundary §8 admits has 0 of 366 samples near it.

**Refuter's correction.** Soften one leg and correct one fact. (a) "§2 says the opposite of the header outright" is overstated — §2's "not specified here" most naturally means its VALUE is not specified, which the header also says; the defect that stands on its own is the header's claim that the ESTIMATION is specified, when no estimator appears anywhere in either document. (b) "the shipped sample carries one acquisition number per segment" understates what is there: `SegmentSample` carries both `total_fetch_us` and `active_fetch_us` beside `bytes` (estimate.rs:259-263), so `total − active` and `active/bytes` are a natural two-parameter decomposition already available. That makes the gap narrower but not smaller in consequence — the spec never mentions `active_fetch_us`, and the window, update law, regime selection and cold-start value are still the implementer's to invent, on a boundary §8 admits has 0 of 366 samples near it.


### [must-fix-before-implementing] §7 row server_cost_weight — server_cost_weight kept on a 4% premium its own evidence refutes
*seat: decision*

**Claim attacked.** "**Keep, and re-measure.** The trade is real (2.1× the work for 4% more bits) but `production_load_pm` is a per-item quantity stored as a per-server constant, and is inert below its own floor for the modal item at every rung (`p2h` §6b)."

**Defect.** The "4% more bits" is the ratio of two catalog `expected_wire_kbps` entries, one of which p2h §6(b) proves the app never obtains; recomputed against the app's own request the trade is 2.1x work for 29% more bits, a 6.6x error in the premium that is the entire argument for keeping the weight. Scope: `server_cost_weight` appears at exactly one site, mode.rs:155, reached only via `hls_utility` ← `choose_mode`, whose three callers (original.rs:141, 233, 478) are all the Original-vs-HLS decision; rung selection is `best_for_budget`/`best_sustainable` (ladder.rs:318-344), `max_by_key(expected_wire_kbps)` with no utility term — so the P1080High-vs-Uhd trade the row cites is structurally unmakeable by this weight. And "inert below its own floor" is `predicted_ratio_pm` (plant.rs:113-121, which clamps at `production_floor_pm`); mode.rs:155 uses `candidate.production_load_pm` raw, with no floor, where `4*load/1000` integer-divides to a constant **3** for all seven rungs 6000–18000 (4·900/1000 … 4·995/1000), 4 at P1080High and 8 at Uhd.

**Consequence.** The one row that says "keep" keeps it on a refuted number, and its live product meaning is not the stated one: it is a flat 3-point head start for Original over the whole 1080p ladder, not a per-rung price on server work. Under the corrected values the pair the plan's §6.3(1) singled out as unreachable (P1080High vs Uhd) scores 72−4 = 68 against 76−8 = 68 — an exact tie the re-measure is supposed to resolve and does not.

**Refuter's correction.** §7's `server_cost_weight` row keeps the weight on "2.1× the work for 4% more bits", a ratio computable only from catalog entries `P1080High` 20 011 and `Uhd` 20 895 (ladder.rs:224-225, echoed at mod.rs:149-151). Recomputed from the raw sweep (`docs/measurements/p2h-logs/movie-*-segments.csv`), the app's own request at that rung returns declared 16 150 kbps, not 20 011 — matching p2h §6(b) and ladder.rs's own doc — so the real premium is 20895/16150 = +29%, not +4%, and 2.1× work for 29% more bits is a weaker argument for charging server cost, not a stronger one. Two further mis-descriptions: (a) the P1080High-vs-Uhd trade the row cites is not made by this weight — `server_cost_weight` has one non-test use (mode.rs:155), reachable only through `choose_mode`, whose three callers (original.rs:141, 233, 478) all pass the same candidate as both current and best, while rung choice is `max_by_key(expected_wire_kbps)` at ladder.rs:322/343 with no utility term; its live effect is a near-constant Original head start of 3 points across rungs 6000–18000 (4·load/1000 = 0,0,1,1,3,3,3,3,3,3,3,4,8). (b) "inert below its own floor" belongs to `predicted_ratio_pm` (plant.rs:115-118), which clamps at `production_floor_pm`; mode.rs:155 applies no floor at all, so that clause does not qualify the row it appears in.

### §5's deadline is evaluated at exactly the rungs §3 refuses to bound
*seat: control*

The central mechanism is a misreading of the predicate's subscripts. `B < A_i + E_tx_down(k*)` takes A at rung **i** — the rung already playing — which is directly observable from that rung's own fetches and needs no predictive σ bound at all; §3's σ exists to bound a rung the transaction has NOT fetched.
