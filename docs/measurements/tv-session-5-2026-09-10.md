## 6. Lifecycle parking (lane C item 4) — PROVEN

**`com.webos.app.home` cannot be the switch target on this firmware.** The webOS 4 launcher is an
OVERLAY: `docs/lg-self-checklist.md` records the 2026-09-04 measurement that the app keeps its pid,
keeps drawing and receives **no** `LIFECYCLE: background`. The target used instead was our own
**stable install** — a full-screen native app we own, launched through
`com.webos.applicationManager/launch` (`luna-send` wrapped in `script -qc`; it needs a controlling
tty, and the payload has to be shipped in a file rather than nested through three levels of shell
quoting, which is what made the first attempt return `errorCode 2 invalid parameters`).

From a playing state at `pos=299s`:

```
LIFECYCLE: background (playing=1)
ff: demux ended
stop_bufferfeed: torn down
LIFECYCLE: background (playing=0)
videoplane: unbound — ordinary idle rules from here
loop=42 route=home fps=42
…
loop=60 route=home fps=0            ← parked and settled while backgrounded
LIFECYCLE: foreground (wasPlaying=1)
LIFECYCLE: foreground (wasPlaying=1)
esInfo: videoFps 24/1 + adaptiveResolution (src 24.000)
load: v=H264 a="AC3" fps=24.000 dv=present:0 P0/0 el:0 atmos:0 max=1920x1080@24
SMP: calling Load (uid=NULL)
…
videoplane: BOUND — the gate presents unconditionally and no frame may snapshot
loop=59 route=player overlay=none pos=301s play=992pm vtick=5 vgap=201ms fps=59
```

Both edges of each pair arrived, exactly as the phase-9 arms assume: the first background edge
reports `playing=1` and the second `playing=0`, because the first arm has already flipped the route
to Home. The plane's FALSE edge is carried on the suspend and the TRUE edge on the reload. Playback
resumed **at the saved clock** — 299 s before the switch, 301 s after, then climbing at ~992 pm. No
panic, no `route`/`trail` disagreement, and the heartbeat is back on `route=player`.

## Failures

### `fps:settings-home` — intermittent, and not in phase 9's diff

Failed twice, then passed twice. The failing runs printed `route=onboard overlay=settings` for every
one of their 17 heartbeats; the scene selects `route=home overlay=onboard`. No `BADTRIGGER` line, no
`settings: boot target timed out`, so the boot target matched and the family opened.

What was ruled out, each with its own run:

| leg | words printed |
|---|---|
| harness, managed test user (×2) | `route=onboard overlay=settings` — FAIL |
| harness, `--owner` | `route=home overlay=onboard`, 60 fps — PASS |
| `tv-session.sh up` by hand, same two triggers, owner | `route=home overlay=onboard`, 58–60 fps |
| the same by hand with `--guest` | `route=home overlay=onboard`, 59–60 fps |
| the same build on `make sim`, with and without the oscillator | `route=home overlay=onboard`, 19/19 samples |
| harness, managed test user, later in the session (×2) | `route=home overlay=onboard` — PASS |

So the app is right on both identities by hand and on the host, and the failure only ever appeared
through the harness's own managed-user boot, early in the session. In the same failing suite
`settings-root`, `-privacy` and `-legal` printed `route=home` as the same identity, so it is not a
plain "this profile boots to Onboard". The mechanism that would produce exactly this pair — the app
on `Route::Onboard` with the family surface up and its inner stack empty (`RouteSurface::top_word`
answers `settings` when `top()` is `None`) — was not caught in the act, and the two by-hand legs
that could have caught it may themselves have changed the profile state that provoked it.

**Not attributed to phase 9**, but not fully explained either. `tv-session.sh up --guest` is worth
fixing first: it prints `guest identity: use tests/run.py … booting as owner` and silently runs as
the owner, so the by-hand "guest" leg above proves less than it looks like it does.

### `fps:cold-open` — over its ceiling, and the phase-9 BASE fails it too

Five samples on 1333f934: no-line PASS, **208.5**, no-line PASS, **191.4**, **227.8** ms against a
`stall_ceiling_ms` of 160 (baseline 143.1 ms, TV session 1, panel ON). The gate grades the largest
`FRAMEDROP total=` on `route=detail` over the whole run; a run reporting "0 FRAMEDROP line(s)" means
the detail mount came in under the detector's threshold, so the distribution straddles the ceiling.
The bad frames are not draw-only:

```
FRAMEDROP total=191.4 … results=50.6 navcommit=12.1 draw=127.2 swap=1.4 up=0  px=0       route=detail
FRAMEDROP total=227.8 … results=49.4 navcommit=12.6 draw=165.1 swap=0.6 up=9  px=1775475 route=detail
```

~50 ms of it is the RESULTS phase (async landings), ~12 ms `navcommit`, the rest a fat `draw=` —
which on this driver is where the GPU wait lands, plus nine texture uploads of 1.78 Mpx in the
second.

**Bisected on the device.** Built `525778e1` (the phase-9 base, i.e. phase 8), deployed it
(`verify-deploy: 16 files match`, md5 `00a83dc1…`) and ran the same scene three times:
**160.9 FAIL, no-line PASS, 172.0 FAIL** — the same `results≈42 navcommit≈9` shape. The overrun is
therefore **pre-existing on the base and not introduced by phase 9**. The phase-9 samples do trend
higher (191–228 vs 161–172) but three samples a side cannot separate that from the noise this gate
already shows. The phase-9 build was rebuilt and redeployed afterwards (md5 back to
`1fcd78b2…`, `verify-deploy: 16 files match`).

## Left open

- **`cold-open`'s ceiling is wrong or the cold detail mount got slower**, on the base as well as on
  phase 9. Either re-baseline the 160 ms ceiling from a run of samples (it was set from a single
  143.1 ms panel-ON reading) or take the `results=50 ms` phase apart — no test in the suite explains
  what an async landing is doing for 50 ms on the frame that mounts a detail page.
- **`settings-home`'s failing mechanism** is uncaught. The next attempt should keep the harness's
  managed-user boot and add `--save-logs` plus a state probe, before any by-hand leg disturbs the
  profile.
- **`tv-session.sh up --guest` does not run as the guest** — it warns and falls back to the owner.
  Because of that fallback, the player tour wrote ~10 s of progress to the owner's account, and a
  later boot that was left playing carried it to 9 m 40 s. It was cleared with the harness's own
  reset (`/:/unscrobble`, the only thing that works — a `/:/timeline` post at `state=stopped&time=0`
  returned 200 and changed nothing, exactly as `docs/agent-reference.md` says of `/:/progress`).
  **That reset also cleared the item's `viewCount` (3 → none)**, which is the cost of the only
  working door.
- **A HUD auto-hide observation for an interactive boot** was not taken; every capture here is
  inside or past the 60 s headless pin, so the 4.5 s linger itself is still only host-tested.
- The panel changed state mid-session (02:40), so the first suite is a mixed-panel run. A
  same-scene screen-on vs screen-off `fps=` comparison — the number `docs/agent-reference.md` says
  is owed — was still not taken.
- `tools/.lanec_addtest.py`, `tools/.lanec_need.json` and `tools/.lanec_need_final.json` are lane
  scratch files that came in with the phase-9 merge and are still tracked.
