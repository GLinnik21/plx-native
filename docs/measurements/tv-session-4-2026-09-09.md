## The Settings family at 40 fps: a second full-screen pass under the opaque ground

Diagnosis, in the order it was done, because each step ruled something out:

1. **Bisect A** — reverting the day's nav lane (`12bf8744`) still read 40. Not that change.
2. **Frame-drop detector** (`plxnative-framedrop`) — every frame ~33 ms, all of it in `draw=`.
   **CPU profiler** (`plxnative-cpuprof`) — `frame.ui` 24 ms with ~4 ms named: GPU time.
3. **Host-cache counters** (a temporary `popover::host` diagnostic, not kept) — the frozen page
   snapshot was `served=60 captured=0` per second: the cache was working, and was being DRAWN.
4. **Draw-mask census** on `settings-root` (`tests/run.py --extra-trigger plxnative-drawmask=<class>`,
   one scripted leg per class):

   | masked class | robust_min loop/s |
   |---|---|
   | (none) | 40 |
   | glass | 40 |
   | text | 40 |
   | rect | 55 |
   | **ambient** | **60** |
   | **image** | **60** |
   | all | 60 |

   Two full-screen passes stacked: the `RouteGround`'s ambient wash (the surface's own ground)
   and one full-screen **image** — the frozen page snapshot quad.

**Cause.** The loop's guard around the page closure read `!host_replaced || page_owned`. Through
phase 7 that was right: `page_owned` meant "the dispatcher draws the page, not the closure" and
no owned page (Favourites, Login, Profiles) could host an opaque surface. Phase 8 made Home an
owned page AND the host of Settings, so both bits held at once; the closure ran under the
opaque ground every frame and `popover::host::page_pass` served the snapshot as a full-screen
`Class::Image` quad beneath the ground's wash.

**Fix** (`6fb7cd7f`): `bridge::page_plan(host_replaced, page_owned)` folds the two bits once
(`Owned` / `LegacyThenSurfaces` / `SurfacesOnly`); a Replaced host is `SurfacesOnly` whoever
owns the page, so no page pass and no quad run. Test
`a_replaced_host_draws_surfaces_only_whoever_owns_the_page` was written against the old mapping
and watched fail first.

**Re-measured** on the fixed build: settings-root / -privacy / -home / -legal median 60 fps
(min 59, floor 50); settings-idle ceiling held; modal-ramp worst 60.1 ms (ceiling 75, the fast
mode of the known bimodal pair); legal-document, decision-alert and home-acct-glass unchanged.

## library-switch at 43–45 against a floor of 45

Three readings on the fixed build: 43, 45 (with `plxnative-framedrop=20` armed) — the fps= gate
passes; slow FRAMES are the failing half. Draw-mask census on this scene:

| masked class | robust_min loop/s |
|---|---|
| (none) | 43–45 |
| glass | 46 |
| shadow / image / text | 44 |
| rect | 47 |
| card | 52 |
| **ambient** | **57** |

The frame-drop log shows sustained runs of ~58 ms frames (`draw=57`, 38 card composites drawn of
which 26 off-screen, no uploads) and shorter runs at 33 and 24 ms. The owned Library carries no
`ui::profile::phase` brackets, so the CPU profiler attributes nothing beneath `main.ui`.

**Cause** (found by the delegated investigation, with its own device runs). `app/bridge.rs::sync_host`
decided which dispatcher surfaces take a `popover::HOST_USERS` share from a hand-written style
list — `Sheet | Opaque{snapshot} | Alert` — that left out `Style::Compact`, whose one production
surface is the Library's Sort/Filter menu. With no host user `popover::host::page_pass` never
froze or cached the page, so the whole Library — wash, shelves, poster wall, every string — was
re-rendered under the open menu on every frame, in eight of the scene's fourteen steps. The
container's own table (`surface_policy`: Compact = Live/Cached), `Style::Compact`'s doc naming
`item_menu` (`caching_host()`) and the legacy menu's `Popover::new().caching_host()` all said
otherwise. The `cards=38 off=26` counters were not a doubled page pass: `take_card_stats` sits in
the frame-drop line's lazy closure and accumulates across presents.

**Fix** (`a82db124`): `modal::style_caches_host(style)` is DERIVED from `surface_policy` and
`sync_host` asks it — the table is stated once. `report.underlay_moving` from the dispatcher is
threaded into the loop for the first time since phase 8 (it was bound to `_report`), so an owned
page's motion reaches the wash's dither gate and `host_refresh`. Regression test
`a_compact_library_menu_holds_a_frozen_host_and_gives_it_back_on_dismissal` (historical red:
`left: 0, right: 1`), plus `every_style_caches_its_host_exactly_when_the_policy_table_says_cached`.
The owned Library gained `ui::profile::phase` brackets: `lb.ground`, `lb.document` (with
`lb.shelves`), `lb.grid`, `lb.rail`, `lb.menu`.

**Re-measured** (unarmed, one lease per run):

(removing it alone re-refreshes the snapshot every frame) and relocating it per surface (§4.4) is
phase 10's ModalStack work, with its own device pass.

## Final pass on the integrated branch (882c9415): 29 passed, 1 failed of 30

Main `d2911957` merged in, both fixes above and the two owner-reported grid regressions (focus pop,
press-dip treatment scale) cherry-picked; run under a subagent's own lease (`/tmp/plx-tv4-final.log`).
Every scene that failed the first pass passed: settings-root / -privacy / -home / -legal at 60 fps,
library-switch at robust_min 54. The one failure is NEW: **modal-ramp** worst robust_max 188.6 ms
(max 210) against the 75 ms ceiling, with every bad frame's `FRAMEDROP` line charging
**`navcommit=` 150–181 ms** — the dispatcher frame that commits the Settings open/dismiss — not
draw or swap. The same scene read 60.1 ms on `6fb7cd7f` earlier in the session, so the cost was
added by one of the commits between (the merge, the menu host-freeze fix, the grid fixes). A
device bisect over that window was delegated — and refuted the premise.

**Bisect** (one lease per commit): fd332023 65.9 ms PASS, c063712a 64.4 ms PASS, 882c9415 194.9 ms
FAIL, c063712a REPEAT 65.3 ms with a 153.5 ms `navcommit` spike of its own, 882c9415 passing in
two of four runs. No culprit commit: the symptom is bimodal and old — the same bimodality session 3
recorded as "65 or 94 ms, cause not understood". Three narrowing passes on the set (`NAVSPLIT` →
`bridge::frame_with_tap`; `DISPSPLIT` → the dispatcher's POST-COMMIT drain, where a mounted
screen's `Enter` runs; `SESSLOAD` → 23 `plex::session::load()` calls in 18 s, `saves=1 plaintext=1`
each) found it: `screens/settings.rs::signed_in()` asked `session::load()` — the
read-modify-WRITE door, which re-persists a plaintext session through `write_atomic` (temp file,
`sync_all`, rename, a second `sync_all` on the directory) because this set has no usable key
manager. `RootPage::rebuild` asked at construction AND on `Enter`: two flash writes and four
fsyncs on the frame that mounts the modal, at whatever latency the flash felt like (6–75 ms each).
`session.rs`'s own doc forbade it beside `peek`.

**Fix** (`2ce865f6`, cherry-picked): `signed_in()` reads through `session::peek()` (same answer —
`load` mints neither the account token nor the server); `person.rs`'s two worker reads join it
(`load` holds `session::IO` across its write, parking the next main-thread `peek`); a new
`sessionwrite` rule in `ci/check-deps.sh` refuses `session::load(` under `screens/` and `ui/`.
Test `opening_settings_never_writes_the_session_file` (historical red: the file's inode moved on
the mount). Re-measured: modal-ramp worst **54.8 / 54.3 ms** in two runs with zero `navcommit`
spikes — below every previous PASSING reading (63–66) by the ~16 ms an open used to spend in
flash; settings-root/-privacy/-home/-legal/-idle 5/5, home-acct-glass 55, library-switch 53.
