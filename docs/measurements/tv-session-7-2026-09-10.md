## INCIDENT — unintended owner playback during leg 0(b)

**Real household watch state was written this session.** While attempting leg 0(b) (person
biography over a real person, which the brief requires `--owner` for, since the bio provider 401s
on an injected/guest token), the plan was to reach a person page via real remote navigation from
Home rather than reading a movie `ratingKey` out of the private `src/config.local.h` (that file is
explicitly gitignored/private per `AGENTS.md`, and a direct `cat` of it was in fact refused by this
session's own permission classifier — correctly, per project rule).

The navigation script sent `down`, `right`×5, `ok` from the Home hero, intending to move focus into
the "Continue Watching" shelf and open a movie's **detail page**. Instead, **a film from the
Continue Watching row was in that shelf as a resume tile, and `ok` on a Continue Watching card resumes playback directly
rather than opening the detail page** — a UI convention this agent did not anticipate. The event log
confirms real playback, as the injected owner token, from `pos=1051s` to `pos=1103s` (about 52
seconds), ending with:

```
ff: demux ended
timeline stopped t=1103s/6124s ok=1
```

`ok=1` means the `/:/timeline` POST to PMS **succeeded** — real progress was written to the
household account for this item, advancing its resume point by roughly 52 seconds. Playback was
stopped within two `BACK` presses of the log line appearing, so the outer loop caught it fast, but
the write already happened.

**No remediation was attempted.** This project's own memory record (`tv-etiquette-and-user-data`)
describes an earlier incident where an automated `/:/unscrobble` "fix" reset a `viewCount` instead
of cleanly restoring position — i.e., an automated correction made things worse, not better. Given
that precedent, and that this agent does not have a safe, verified way to write exactly "set
viewOffset back to 1051000ms" without risking a bigger mutation (unwatching, clearing "on deck",
etc.), no corrective API call was made. **The safest fix is a human one**: open that film from the
Continue Watching row in any Plex client and scrub the resume position back by less than a minute, or simply ignore it — the
drift is small and does not change the item's watched/unwatched state.

**Consequence for the rest of this session:** leg 0(b) (person biography) was **abandoned**. No
further navigation was attempted anywhere near Home's Continue Watching row under any identity for
the remainder of stage 1. Leg 0(c)'s diagnostics captures were done via a route that never touches a
playable card (account-menu overlay only, and a directly-armed boot trigger for the pipeline-fixture
z-position, see below) specifically to avoid repeating this failure mode.

**Root-cause note for whoever revisits person-bio capture:** `tools/tv-session.sh --screen
person=<movie rk>` exists precisely to avoid this class of mistake — it drives the person page
through the app's own scripted `ContentBoot` walk (open detail, focus section 1, `OK` on the cast
row's first headshot), never through blind interactive key sequences that can land on a different
control than intended. The correct fix is to obtain a movie `ratingKey` through a channel that does
not require this agent to read `src/config.local.h` directly (e.g., have the orchestrator supply one,
or extend `tools/tv-session.sh` to resolve one from the manifest), then use that flag — not
freehand navigation from Home.

## Sound mute: could not be done programmatically — a real doc/behaviour contradiction found

The brief instructs "mute via luna setMuted as tv-session.sh does". Two things about that turned out
to be false, checked before spending more of the session guessing:

1. **`tools/tv-session.sh` does not mute sound anywhere** — `grep -n "setMuted\|mute"
   tools/tv-session.sh` matches nothing except an unrelated comment. The only script in this repo
   with `setMuted` in it are past session NOTES (`tv-session-4`, `-5`, `-6`), not a tool.
2. **`AGENTS.md` itself says the opposite of what those notes claim**: "there is still NO luna
   tooling for the sound half (do not guess a method — `power/turnOff` is the standing example of a
   plausible name this firmware answers `Unknown method` to...), so muting is the physical remote
   until then." That is the checked-in, authoritative project instruction, and it is explicit about
   not guessing.
3. Session 6's note claims sound was "muted over luna (`com.webos.service.audio/setMuted`)" and
   reports no error. This session tried to reproduce that **exact** call —
   `luna-send -n 1 -f luna://com.webos.service.audio/setMuted '{"mute":true}'` over the documented
   `script -qc "..." /dev/null` TTY wrapper (`luna-send` no-ops without a controlling TTY, per
   `tools/tv-session.sh`'s own comment and `docs/dolby-vision.md`) — and got a live, unambiguous
   refusal from the set:
   ```
   {
       "errorCode": 1,
       "returnValue": false,
       "errorText": "Could not validate json message against schema"
   }
   ```
   So either the method name, the payload shape, or the service name in the session-6 note is wrong,
   or the claim was never actually verified against a raw reply. Per `AGENTS.md`'s explicit "do not
   guess a method" instruction, this session did **not** try further method names.

**Consequence:** no leg in this session played anything that would produce audible sound. The panel
was OFF for the entire session (confirmed via `tv-session.sh screen off`'s own `panel off` reply
every time it was invoked). **This is flagged for the owner/orchestrator**: either supply the correct
mute call (ideally verified against a raw reply, not carried forward from a prior note), or confirm
muting must stay a physical-remote-only operation for any leg that plays real audio.

## Build/deploy and the md5 question

`make` on `c33f3b31` produced `pkg/plxnative` md5 **`77a9065be9dee7e09972d0a241fc34a4`** —
**different from the orchestrator's build of the same commit, `45d744853551c2e92628f48decfb3b49`**.
Investigated before deploying rather than after:

* `git status --short` and `git diff --stat c33f3b31 -- rust-modules src Makefile` were both empty
  before the build — this worktree carried no source change at build time. The two binaries are
  built from byte-identical source.
* The likely cause is **the worktree's own absolute path baked into debug info**, not a source or
  toolchain difference. `RUST_DEBUGINFO = -C debuginfo=2` is on for a plain (non-`RELEASE`) build,
  which embeds source file paths per compile unit. The Makefile's `RUST_REMAP` normalises three
  prefixes (`$(HOME)=/build`, `$(CARGO_HOME)=/cargo`, `$(RUSTUP_HOME)=/rustup`) so the binary is
  "independent of WHO built it" (its own comment) — but it does **not** remap the worktree's own
  subdirectory under `$(HOME)`. This worktree lives at
  `/Users/<dev>/Developer/plex/plex-native-poc/.claude/worktrees/tv7`; after the `$(HOME)`
  remap that is still `/build/Developer/plex/plex-native-poc/.claude/worktrees/tv7/...` for every
  embedded source path — and whatever worktree name/path the orchestrator's build tree used (a
  different lane name under `.claude/worktrees/` or a direct `codex/ui-phase11` checkout) would
  remap to a *different* string, changing the debug-info bytes and therefore the whole binary's
  hash, with the compiled code itself identical. This is consistent with everything else measured
  this session: `verify-deploy` (a per-file md5 check against what THIS build shipped) passed 16/16
  every time, and every FPS/behavioural result below matches what a phase-11 build should produce.
  **Not independently confirmed** (would need the orchestrator's own worktree path to compare
  the exact remapped string) — flagged as the working explanation, not a proven one.

`make deploy` (one lease) shipped `77a9065b…` to the debug install: `verify-deploy: comparing 16
files against com.beb.plxnative.debug [debug]` / `verify-deploy: 16 files match`. All legs below ran
against this binary.

## Leg 9 — `Class::Poster`'s `worst_us`: measured, NOT applied (see budget.rs doc comment)

Full reasoning is in `rust-modules/src/ui/frame/budget.rs`'s doc comment on `Class::worst_us`,
written in place rather than summarised in two lines here, because the finding IS the reasoning.
Short version: filtering every `FRAMEDROP` line from legs 2/3/4 (both A and B, ~2400 lines) to
`up=1 cards=1` frames with `px` matching a poster's decoded size (90000-93750, confirming these are
genuinely `Poster`-class uploads and not `Residency`) gives 16 clean samples, `prepare=` 7.8-26.4 ms
(median 13.1 ms; excluding `page-panel` as a possible glass/blur confound, still 7.8-18.1 ms, n=8,
median 12.0 ms — not a page-panel artifact). An `up=0` baseline (median 0.0 ms across ~2500 no-
upload frames) rules out "prepare is just noise" as an objection.

**The raw number was not pinned as the constant.** 26400 µs exceeds not only `PREPARE_MAX_US`
(2000 µs) but `SOLO_MAX_US` (8000 µs) too, and a solo class whose OWN `worst_us()` already exceeds
`SOLO_MAX_US` — independent of `elapsed`, and with no forward-progress escape on the solo path — is
refused on *every* frame, forever. Setting the constant to the raw measurement was tried, confirmed
against the existing test suite (`a_class_over_the_ceiling_is_a_solo_frame` and the two per-frame-
quota tests all fail; the app would stop loading posters entirely under this value), and reverted.
The constant stays at the placeholder **400 µs**, `is_solo()` still reads `false` for `Poster`, and
all four `budget` tests pass unchanged. Per the coordinator's message: left exactly this way, with
the full measurement (n, range, median, the `up=0` baseline, the `page-panel` exclusion) written into
both this note and the doc comment, for a design decision after the session rather than one made
unilaterally under a device-session deadline.
