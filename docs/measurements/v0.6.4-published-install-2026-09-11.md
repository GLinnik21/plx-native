# v0.6.4 published-package and migration checks

Post-publication evidence, recorded separately from the immutable release note and generated
release audit. No media was played during these checks.

## Published artifact

- [Release v0.6.4](https://github.com/GLinnik21/plx-native/releases/tag/v0.6.4) was produced by
  [workflow 34599339828](https://github.com/GLinnik21/plx-native/actions/runs/34599339828), from
  maintenance commit `391c74d0`.
- All five jobs succeeded: bump/tag, tag/version agreement, redistributable assets, build/verify,
  and publish. The workflow uploaded the Sentry symbols and generated the release audit.
- A separate `ci/verify-published.sh v0.6.4` run passed all seven checks. The package, checksum,
  manifest and release-note hash agree; every asset uploader is `github-actions[bot]`.
- The Homebrew Channel listing uses the latest-release manifest URL; GitHub's latest release was
  v0.6.4 when checked. No listing or compatibility-bound change was needed.

## Installation through the actual installer

The public stable IPK was downloaded and checked against its published checksum, transferred to
the development TV, and installed through `com.webos.appInstallService/dev/install`. The installer
reached `state=installed`. No subsequent deploy replaced its binary. The installed executable's
SHA-256 matched the executable extracted from the public IPK.

The app identified itself as `com.beb.plxnative`, `features=release`, with production reporting
endpoints configured. No remote-input FIFO or capture listener on port 8910 was present.

Before this first update, the existing stable session file was already mode 0777. The backup made
before installation proves that, and comparison immediately after installation proved the
installer had not changed the saved files. At launch the existing trust policy quarantined that
write-widened file rather than trusting its contents. That policy is present in both v0.6.3 and
v0.6.4; this observation does not establish how the earlier file acquired those permissions.
The original bytes remain recoverable in private backups; none are included in this report.

## Explicit clean 0.6.0 → 0.6.4 migration

At the user's request:

1. Installed the published stable v0.6.0 package and verified the installed executable against
   that package.
2. Stopped the app and cleared its local stable data after explicit user authorization, retaining
   private recovery copies outside all app candidate paths. Debug data was not touched.
3. Confirmed v0.6.0 booted with no session. The user completed a fresh sign-in; the log recorded
   authorization, server discovery and the resolved-server handoff.
4. Stopped v0.6.0 and backed up the resulting saved data. Its session file was mode 0600.
5. Installed the public v0.6.4 package without clearing data, restoring another session or changing
   file permissions. GNU tar's comparison against the signed-in backup passed before launch.
6. The new v0.6.4 process read `developer:plaintext`. Cold eligibility was account=1, PMS=1,
   server=1, local=1. The boot selected the stored-session/profile-picker path, not QR sign-in.
7. The user completed the reporting-scope question/profile selection and confirmed successful
   entry. The log recorded `login: server installed — entering Home`.

This directly verifies retention of an ordinary v0.6.0 sign-in across an installed v0.6.4 update
on the development television. The new reporting-scope question is not account reauthorization.

## Diagnostic delivery and remaining limits

The native one-off receipt `4175abcfc8948826378a90b3302e1650` was rechecked in development Sentry.
It carries the cold `developer` storage error, `secure_unavailable` / `no_reply`, sealed identity
and registration flags, plus webOS and hardware context. It was sent while the selected spool
filename was deliberately occupied by a directory and standing reporting was off. The complete
experiment and restoration are in the [reassessment ledger](issue-76-reassessment-2026-09-11.md).

The development TV has no real keymanager3. The fake-service recovery test and this plaintext
migration do not prove the reporters' exact cause, real-keymanager3 behavior, or a TV power cycle.
Fresh-save error/readback serialization is covered by host regressions, not by that cold-read
receiver event. Reporters' new-device outcomes still require their own diagnostics.

A separate minor UI observation remains: with the legacy reporting-extension explanation above
the main consent text, its last phrase can be ellipsized. The full Privacy document is accessible;
this did not block sign-in or migration and is not an authorization loss.
