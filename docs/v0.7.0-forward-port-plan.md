# 0.7.0: перенос окончательных решений 0.6.6

Статус: согласованный план реализации и проверки; перенос ещё не выполнен. Исследование кода не является подтверждением работоспособности кандидата.

## 1. Основа, границы и результат

- Источник поведения — опубликованный `v0.6.6`, `48866094e73493eb57a045723cdb6e195d9f4361`.
- Исследованная архитектура назначения — `4b390cdd2d830617c074f76dd7cf8a6bb97ee2d7`; выбранная база — `c8a0ed655b2ae70b08f37cccfa3d7b35a51452a0`, добавляющая только исправление CI #93.
- Перед реализацией сверить refs с этими SHA. Если main изменился, Sol классифицирует добавленный diff и обновляет базу и затронутые доказательства. Нельзя молча проверять другую ревизию.
- Пользователь остановил UI-рефакторинг. Незавершённый Person-worktree не включать, не менять и не очищать. Browse/ViewState ownership и существующие слои совместимости сохраняются; завершение всего UI-рефакторинга не является условием выпуска.
- Переносить окончательные решения по подсистемам, а не последовательность исторических патчей. Исторические исправления служат источником регрессионных сценариев.
- Результат — 0.7.0 со всеми актуальными исправлениями шестой линии, сохранёнными возможностями седьмой и проверенным обновлением существующей установки. После выпуска обычная поддержка переносится на седьмую линию; `release/v0.6` сохраняется как история.

## 2. Хранение и Session

### Каноническое хранилище

Перенести `storage`, `storage_service`, клиент helper и ограниченный FIFO из финальной 0.6.6. Сохранить `<appid>.storage` как владельца приватного DB8 kind, раздельные stable/debug identities и фиксированные ID записей, внешнюю схему состояния и протокол helper версии 1.

DB8 хранит `_id/_kind/_rev/state`, где `state` — непрозрачная JSON-строка. Сохранить узкий reader ранее появлявшегося flattened-формата; не возвращать вложенные Session/Consent-объекты под преобразование DB8. Сохранить CAS, журнал операций, сверку uncertain по прежнему operation ID, двухфазное обновление защищённых credentials, UID/permissions/handshake и тайм-ауты socket-протокола.

На ARM DB8 — единственная действующая authority Session/Consent. Старые файлы — только migration inputs; файловый backend остаётся для host/simulator. Обычный refresh не понижает защиту ciphertext. Политика Keymanager/ACL остаётся финальной из 0.6.6: majors 1–4 используют предусмотренный ACL-tier; свежая авторизация и импорт на новых/неизвестных версиях допускают диагностируемый fallback после попытки Keymanager, routine refresh — нет.

### Объединённая схема

| Данные | Назначение |
|---|---|
| Client ID | Существующее public-поле |
| Quality, auto-sign-in, last-library, last-hero-blur | Public preferences |
| Home pins, recents | Существующие public-разделы |
| Account/profile/server tokens, roster, sources | Защищённый Session payload |
| Кэш профилей и PIN-verifiers | Типизированное поле защищённого payload v2 |
| Consent/scopes/reporting IDs | Отдельные существующие слоты Consent |

Читать protected Session v1 без изменения записи; переходить в v2 при первой записи, меняющей защищённые данные. Чтение и public edit не вызывают перешифрование. Helper обрабатывает plaintext как непрозрачное содержимое, поэтому его протокол, внешний schema и crypto context не меняются.

Не активировать credentials из произвольных `extensions["profiles"]`. Прямой импорт текущего dev-формата переносит типизированные `Session.profiles`. Сохранить механизм неизвестных полей 0.6.6, включая вложенные записи; зарезервированное непрозрачное `profiles` при миграции не становится активным кэшем v2. V2 пишет только типизированное поле и отвергает неоднозначную коллизию с зарезервированным extension.

V2 требует массив profiles; неправильный тип — ошибка protected schema, без fallback. Повреждённый элемент исключается из offline-кэша, не уничтожая основной аккаунт. Проверять непустой UUID, `uuid == user.uuid`; при дубликатах исключать все записи данного UUID. Присутствующий PIN-verifier проверяется на salt 16 bytes hex, hash 32 bytes hex и iterations `1..=MAX_ITERS`. Повреждённый verifier нельзя превращать в отсутствие PIN. Требование PIN определяется защищённостью профиля; закрытый auth не разрешает cached/offline activation.

Кэш профилей переносится только внутри того же аккаунта/tenure. Fresh account replacement начинает пустой кэш и добавляет подтверждённые online credentials. Public edit не записывает пустой кэш поверх locked auth.

`last_hero_blur` сохраняется как существующая optional public-подсказка: default/malformed → None, запись только при изменении, ошибка не блокирует auth. Новый cache subsystem и новый путь не нужны. Отсутствующие auto-sign-in/last-library/profiles получают false/пустые значения; качество сохраняет текущий default Original.

### Миграция

- Валидная DB8 0.6.6 имеет приоритет и открывается напрямую. Прямые обновления 0.6.0–0.6.5, DB8 0.6.6 и текущий dev-формат проверяются отдельно.
- Legacy import разрешён только для отсутствующего/ещё не мигрированного домена. Timeout, недоступность helper, corruption, unknown schema и locked auth не означают Missing.
- Сохранить финальный порядок кандидатов и reader старых Keymanager identity-вариантов. Versioned Data/Cleared wrapper разбирается до bare Session; Cleared переносится как tombstone.
- Удалять источник только после durable write, точного readback и подтверждения защищённого plaintext; старой ledger receipt недостаточно.
- Canonical Cleared/ClearTenure имеет приоритет над вновь появившимся старым файлом. Session/Consent — независимые migration domains одной записи.
- Unknown secure format сохраняется до явного clear. Недоступный известный envelope не удаляется автоматически.
- Protected v2 не открывается обратно в 0.6.6; downgrade не поддерживается и явно описывается перед обновлением.

### Owner protocol и обычные записи

Сохранить SessionMachine, SessionAdapter, CredentialPatch, проверки request/epoch/endpoint и ProfilePublisher. Не переносить старый global auth controller или whole-session save поверх устаревшего snapshot.

Разделить разрешение владельцем, admission и durability. Добавить `PersistenceAdmission` и `PersistenceCompletion`, отличные от существующего auth Landing Receipt. Correlation: request, epoch, arrival, revision, purpose. Каналы/receipts остаются в adapter; owner хранит логическое Pending/Durable/Uncertain/Failed/Superseded.

Проверка permit, merge CredentialPatch с последними preferences и enqueue выполняются одной короткой согласованной операцией; I/O только в worker. Authority различает PublicOnly, Routine и FreshReauthentication. Последняя выдаётся только подтверждённой новой авторизации и не приобретается обычным Retry.

Adapter опрашивает receipts один раз за frame и доставляет типизированные результаты через dispatcher. Callback не вызывает owner рекурсивно. Stale completion не активирует registry/profile, не очищает новую ошибку и не освобождает чужие admission credits.

При неподтверждённом сохранении нового входа предупреждение блокирует соответствующий discovery/final переход до acknowledgement. Discovery warning не расходует fresh authority и не запускает final save преждевременно. После acknowledgement действующие runtime credentials могут использоваться, но не объявляются сохранёнными. Ошибка background refresh не возвращает на QR.

Quality, pins, last-library, recents, auto-sign-in и hero hint используют public-only background updates. Setter bool означает admission/change, не durable. Queue refusal не должна терять dirty edits. Retry использует latest snapshot и expected revision; старый результат не скрывает новую ошибку.

### Boot, logout и replay

Загрузить Session/Consent асинхронно до обычных экранов. Сохранить приоритеты dev boot, auto-sign-in, picker/PIN, offline boot и settings restoration. Failed load показывает Retry этапа, не пустую Session. Settings/draw/focus/Plex-client construction читают готовые snapshots.

Logout немедленно закрывает telemetry/access, отменяет auth workers, отзывает credentials и меняет epoch. Затем общий FIFO проводит telemetry cleanup и один Session ClearTenure для обоих доменов. Consent Delegated связывается с результатом общей операции, не считается Durable. Новый login разрешён после confirmed clear; Failed/Uncertain остаётся видимым Resetting с Retry. Cleanup residue после durable clear показывается отдельно и не блокирует relogin. Старые queued writes отвергаются storage tenure, не только UI correlation. Сохранить существующую очистку принадлежащих аккаунту recording artifacts.

Сохранить ограниченный controlled bootstrap/replay. Новые логические формы получают соответствующие shape/hash/fixture updates; physical receipts не сериализуются. Fixture/replay adapters не исполняют live storage/network. Полный auth replay не является скрытым условием переноса.

## 3. Consent, диагностика, UI и native

### Consent и telemetry

Перенести финальные POLICY_VERSION/NOTICE_REVISION/ERRORS_SCOPE/USAGE_SCOPE = 6. Тот же сбор данных в 0.7 не создаёт новый scope.

- Legacy No остаётся No. Legacy Yes сохраняет прежний scope; extension спрашивается только у включённой категории, если он ещё не принят и не отклонён.
- Decline extension сохраняет канал, ID и accepted scope, меняя только declined scope. Accept сохраняет ID и расширяет только выбранную категорию. Изменение соседней настройки не принимает extension.
- Profile switch сохраняет Consent; account logout очищает обе категории и IDs.
- Owner получает Extend/Retry и разделяет requested/effective/persistence. Withdrawal закрывает gates немедленно.
- Enable сначала делает prospective cutoff: purge/watermark/native cleanup. При успешном cutoff выбор может действовать в текущем запуске даже при Failed/Uncertain save, с уведомлением effective-but-unsaved. Failed cutoff/admission оставляет enable неактивным (NotApplied).
- Completion публикуется только для актуальных revision/tenure. No→Yes не использует старые IDs/records. Sender повторно проверяет revision/scope перед отправкой.

Перенести signin/storage/oneoff serializers, producer/send scope gates, queue/spool и bounded deferred diagnostics вместе. Sign-in standing reports требуют Errors 5; storage details/errors — Errors 6; playback additions — соответствующий Errors 4; `session_storage` usage property отсутствует до Usage 6. Старый разрешённый baseline продолжает работать после отказа от extension.

Активные spool/watermark живут в runtime; persistent retired queues удаляются, не импортируются. One-off требует отдельного Send, не содержит постоянных reporting IDs, различает queued/sending/sent/failed и сохраняет ограниченный direct fallback при ошибке spool. Standing No не отменяет отдельно разрешённый OneOff; logout очищает все категории и инвалидирует fallback generations. Уже начатую сетевую отправку нельзя объявлять отозванной.

Добавить closed-enum rtkmem/install/session_storage context согласованно во все serializers/previews. Обновить C-definition, Rust extern и caller `plx_sentry_set_webos_context` вместе. Сохранить имеющийся window wrapper.

В net сохранить RequestFailure, ResolvePin, curl-version/TLS/CA и правила достоверности HTTP status main. Новую безопасную transport evidence передавать с конкретным request/attempt; source global LastCall не становится authority. При необходимости curl code добавляется на transport boundary, без URL/body/raw error-buffer.

### Owned UI

Login получает Details, сохранение/Retry и one-off report через Session views и typed effects. Consent получает per-category extension и точные applied/saved статусы. Settings mount/draw остаётся read-only.

Добавить owned PersistenceNotice в общий ModalStack для ошибки, завершившейся после ухода со страницы. Аргумент: owner/tenure/revision/message kind. Owner сохраняет право Retry и pending notice, bridge допускает поверхность при свободной общей модали. Новое решение/logout инвалидирует notice даже во время dismiss; stale Retry не действует.

В DecisionAlert перенести Neutral/Destructive tone, left alignment, измеряемый multiline title и полный disclosure без прежнего четырёхстрочного обрезания. Сохранить frames(), Engine focus/hits и блокировку нижнего экрана во время opening/dismiss. Не возвращать source key/press_at input ladder. Экранные подтверждения используют текущий образец ConsentPage; Details и report confirmation не перекрывают друг друга.

Legal/Privacy/previews обновляются под фактическую DB8 authority. Не копировать оставшуюся в source устаревшую прозу об app-local live fallback. IPv6 и последующие multiline-log улучшения main сохраняются.

### Starfish и sandbox

Перенести C LOAD_RETURNED dispatch gate, сохранив значение sf_ready «объект существует». Clear до открытия ready и на error/quarantine/destroy; set после возврата настоящего Load. Rust Shared хранит epoch-scoped InFlight/Returned timestamps; mark return предшествует публикации route result. Даже sf_is_load_completed не вызывается до разрешённой границы.

Сохранить два независимых 20-секундных budget: issued→return и return→loadCompleted. Потеря Active при ожидании завершается failure; stale epoch не открывает новый session. LoadTimeout отличается от pipeline refusal и сбрасывается с native session. Engine остаётся в PlayerAdapter; C gate не покрывает ACB напрямую, поэтому проверяются все ACB callers и stage/bind ordering.

Добавить финальный k5lp/k3lp preflight. Cached device fact остаётся process-wide, ранний getter не инициализирует ложное NotApplicable. Refusal принадлежит Player/PlaybackSession, очищается при exit/reset; обычный start приводит к error screen без Engine, tracked start завершает ticket через существующий rollback.

Repair: owned confirmation с Cancel по умолчанию → typed PlayerReq → resource adapter с MainThread. Логическое состояние попытки живёт у app owner и переживает пересоздание PlayerScreen. Одна принятая попытка на запуск, включая timeout; повтор — после relaunch. Сохранить strict app-id/path validation, root HBC, фиксированную команду, exact result marker и fresh readability check. Ни boot, ни обычный Play repair не запускают. Success требует relaunch, cached preflight самопроизвольно не снимается.

Background/window breadcrumbs и video-plane-owned present/opaque policy main сохраняются. Добавить только WindowActivity::telemetry_activated для async activation, учитывая foreground. Source system.rs целиком возвращал бы старую route-based policy.

## 4. Исполнение и упаковка

Одна integration branch от выбранной базы; промежуточные commits по компонентам, финальная интеграция в main одним squash. Разрешение на публикацию не подразумевается самим выполнением подготовительных тестов.

| Этап | Результат / зависимость |
|---|---|
| A. Storage foundation | Core/helper, production transport injection, schema, migration fixtures |
| B. Session + Consent integration | После A: общий FIFO, owners/adapters, boot, reset; один ответственный за связанные app-файлы |
| C. Diagnostics + owned UI | После протоколов B: scope-aware outputs, notices, readouts, common dialogs |
| D. Native + Repair | Может разрабатываться независимо от A; shared app/telemetry integration выполняется последовательно |
| E. Candidate | Полная проверка, review, doc-claims, упаковка, release preparation |

Не делить одновременные записи в bridge/registry/boot между агентами. Fleet/worktree/TV правила репозитория обязательны; канонические навыки определяют команды. Разные модели не означают независимые resource lanes. В исследовании новые worktrees не нужны; для реализации используются отдельные принадлежащие задаче checkout/build roots. TV доступ только у одного исполнителя под lock.

Упаковка расширяет main: helper build, native service descriptor, package membership, `database.operation`/`securitykey.operation`, обе flavor identities. Helper имеет отдельный auxv shim и не линкует app getauxval.o. Использовать текущий linker wrapper; helper получает собственные map/trace/receipt, единственный getauxval и firmware/ELF evidence.

Проверять настоящий IPK: helper/service identity, permissions, ARM ELF, executable mode/ownership, отсутствие credentials/state/socket/replay artifacts. Включить helper в source reconstruction и firmware imports. Сохранить текущую лицензию, source-release gates и recorder privacy checks; не копировать старые tooling-файлы целиком и не переносить RELEASE_LINE=0.6.

## 5. Методика проверки разными моделями

### Роли и независимость

| Роль | Модель / effort | Ответственность |
|---|---|---|
| Руководитель | `gpt-5.6-sol` / `medium` | Контракты, assignment, coverage ledger, последовательность интеграции, проверки и приёмка по доказательствам |
| Исследователь/проверяющий | `gpt-5.6-terra` / `medium` | Извлечение поведения source, сценарии, эталонные наблюдения, differential checks, doc-claims и чувствительность тестов |
| Архитектурный reviewer | `gpt-6-astra` / `high` | Ownership, concurrency, persistence/security, native ABI и достаточность доказательств |

Sol указывает модель и effort явно при запуске. Если harness не может применить настройку, это отмечается как ограничение, а не выдаётся за выполненное назначение. Автор реализации не является её единственным проверяющим; свежий review получает контракт и артефакты, а не только пересказ автора.

### Паспорт каждого компонента и эталон

До реализации Terra составляет паспорт: requirement ID, initial state, action/event, observable outcome, persisted outcome после restart, разрешённые side effects, failure behavior, source code/test/evidence. Каждый существенный пункт разделов 2–3 обязан иметь ID. Release notes помогают найти требования, но не являются единственным oracle.

Использовать семейства IDs: STORE (canonical/helper/migration), AUTH (owner/boot/logout), PROFILE (PIN/cache/settings), CONSENT (scopes/effective/durable), REPORT (shaping/send/privacy), NATIVE (Load/repair), UI (focus/modal/readout), PACKAGE (artifact/update).

На неизменной 0.6.6 воспроизвести сценарии и записать нормализованные наблюдения. Затем тот же сценарий запускается на конкретном SHA 0.7. Сравниваются результат, сохранённые значения, доступные действия и side effects, а также необходимый причинный порядок. Не требовать совпадения внутренних классов, числа callbacks и порядка независимых событий.

Нормализация скрывает случайные ID, absolute time и private paths, но сохраняет отношения: ID не изменился, operation относится к тому же аккаунту, withdrawal предшествует worker completion, stale epoch отвергнут. Сравнивать partial order и относительные deadlines, не буквальные wall-clock timestamps.

До запуска сравнения отдельно зарегистрировать ожидаемые отличия: protected v2, отсутствие downgrade, новые поля 0.7, owned UI representation. Они не отменяют preservation старого поведения. При найденном дефекте самого source Sol фиксирует отдельную коррекцию с регрессией и review; нельзя молча объявить новое расхождение эквивалентностью.

### Два адаптера, один сценарий

Сделать thin adapters для source и target: translate command → реальный production path → collect observation. Сценарий и assertions общие. Adapters не принимают решения о миграции, durable, consent или допуске входа. Для нового owner protocol сравнивать semantic outcome, а не старый private API.

Инъекции external I/O должны достигать production coordinator/client/backend. Отдельно доказывать факт выполнения нужной ветки. Файловые cfg(test) migration tests source не подтверждают ARM DB8 adapter. Добавить injectable helper transport для production path; actual service/package проверяется на ТВ.

Для полей, которых нет в 0.6.6, применять прямые invariants/round-trip tests и проверку совместимости чтения v1; старый бинарник не является oracle для новых полей.

### Обязательная матрица сценариев

Сохранить существующие ResolvePin/HTTP evidence/IPv6/focus/profile/PIN/playback regression suites.

### Проверка чувствительности

Terra в отдельном принадлежащем проверке checkout временно вносит ограниченные поломки: убрать epoch check, объявить Durable до readback, разрешить fallback после helper error, убрать scope gate, открыть native gate раньше. Каждый соответствующий сценарий обязан упасть по ожидаемой причине. Мутации не интегрируются и не выполняются на ТВ или в чужом worktree.

Факт отказа компиляции не подтверждает поведенческую чувствительность. Для native gates дополнительно сохранить positive control: тест действительно вошёл в in-flight окно и после его закрытия допускает нормальный вызов. Требуется RED→GREEN для исправляемых регрессий, а не только зелёный suite.

### Когда нужен Astra

Три завершённых review-пакета:

1. Storage + Session + Consent: schema/migration, authority, shared FIFO, ClearTenure, поздние результаты и account boundary.
2. Native + Repair: C/Rust ABI, Load/teardown, ACB order, one-shot repair и владение состоянием.
3. Итоговая интеграция: межкомпонентные сценарии, scope completeness и соответствие acceptance evidence конкретному кандидату.

Astra получает паспорт, exact SHA/diff, команды, test artifacts, mutation results и ограничения. Проверяет также качество oracle и отсутствие обхода production пути. Замечание содержит нарушаемую гарантию, начальные условия и воспроизводимый порядок событий; verdict — ACCEPT или REQUEST CHANGES с severity.

После исправления повторяется затронутый пакет и зависимые tests; полный дорогой аудит заново требуется при изменении контракта/архитектуры. Sol не запускает Astra на каждую мелочь, ожидание или повтор неизменного статуса. Неоднозначность security/concurrency/native поведения, расхождение эталона и сомнительный тестовый oracle — основания для эскалации.

### Ledger и evidence bundle

Sol ведёт `docs/v0.7.0-forward-port-verification.md` (создать при начале реализации). Для каждого требования:

`ID → source SHA/evidence → scenario/test → source result → target SHA/result → tier → artifact → reviewer → verdict`.

Допустимые verdict: **совпадает**, **согласованное отличие**, **регрессия**, **не доказано**. Pending/not run имеет verdict «не доказано». Пустой список review findings или зелёный host build не заменяет runtime evidence.

Bundle содержит contract, exact revisions/tree state, commands/toolchain/flavor/features, нормализованные observations/diff, результаты чувствительности и ограничения. Исходные private recordings/configuration не коммитить; tracked ledger содержит только безопасные выводы, synthetic fixtures и ссылки на допустимые artifacts. При смене SHA Sol отмечает результаты, требующие повторной проверки; source baseline остаётся неизменным.

Для каждой задачи Sol передаёт точные SHA, IDs требований, owned paths, scope, команды, ожидаемые artifacts, dependencies, device permissions и условия эскалации. Приёмка разрешена только когда нет необъяснённых regression/unproven по обязательным контрактам, expected differences зарегистрированы и обязательный review закрыт.

## 6. Финальная приёмка и выпуск

Пройти полный make check, shipping no-default-features check с CARGO_INCREMENTAL=0, ARM app/helper, package/ELF/source-rebuild gates, firmware-compat review и doc-claim audit. Команды и tiers определяются which-tier/cut-release и профильными навыками; не подменять native результат hostsim stub.

Simulator: inspect Login/Details/report, Consent extensions/Settings, delayed failures, PersistenceNotice, полный disclosure, focus/hits и все Repair presentation states. Screenshots открываются и проверяются, одного сохранения файла недостаточно.

TV: один назначенный исполнитель под lock, реальные package bytes и install identity. Проверить update 0.6.6→0.7 без uninstall, непустые настройки, новый процесс и power cycle; отдельно старый-file import. Проверить playback/seek/stop/resume/background/foreground, pixels/FPS. Final stable acceptance использует release-configured package без последующего наложения локального бинарника; FLAVOR=stable RELEASE=1 на каждой build/package invocation. Тестовую отправку отчётов направлять в controlled fixtures/endpoints; production Send требует соответствующего разрешения.

Разделять ограничения: старый ТВ не доказывает newer-TV Keymanager; holdload задерживает Rust flag после возврата C и не воспроизводит настоящий зависший C Load; здоровый ТВ не подтверждает Repair на affected chassis. Эти существующие ограничения остаются явно отмеченными и не становятся новыми claims о совместимости. Основной upgrade/runtime путь должен быть проверен на доступном устройстве. Необязательный внешний hardware gap допускается только как явно сохранённое ограничение, а не как PASS.

После приёмки кандидата — один squash в main; version 0.7.0, notes/audit, release CI, проверка реально скачиваемых artifacts. Финальные notes/audit связываются с exact candidate и не расширяют runtime compatibility по статической symbol matrix. Публикация выполняется в рамках отдельного действия выпуска; методика проверки сама по себе не запускает release workflow.
