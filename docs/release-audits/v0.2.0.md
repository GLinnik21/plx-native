**What is not established.** The bundled FFmpeg is the substance of this release and it was exercised on one television only. "Playback behaves the same on every television" is an argument from construction — the same library on every set — and not an observation; no set other than the developer's had run this build when it was published.

None. @mariotaku's report on webOS 6 and 10 ([apps-repo#224](https://github.com/webosbrew/apps-repo/pull/224)) arrived on 2026-08-09, three days after this release was published, and belongs to v0.2.1's record rather than this one.

## Compatibility tiers, and what moved

| Tier | Firmware | Evidence |
|---|---|---|
| Plays video, verified | 2019 LG sets (platform release 4.10) | A human watching the dev set |
| Starts | webOS 4.4.2 through 11.2.0 | The static matrix below: **nine of fourteen images OK**, against two for v0.1.0 |
| Does not start | webOS 3.9.2 and older | The same matrix |

**Two lines moved and both are machine-visible.** `DT_NEEDED` drops from **21 entries to 15**: `libAcbAPI` and FFmpeg are no longer linked by name but resolved at run time by candidate list, which is the entire reason the ceiling comes off. And three FFmpeg shared libraries appear in the payload for the first time. Neither move is a playback claim on any new firmware — the matrix grades startup, and playback on webOS 5.0 and newer had still never been observed by anyone at this date.

## Known issues at release, with provenance

- **Playback on webOS 5.0 and newer is unproven and expected to fail.** On 5.0 LG removed the mechanism that binds decoded video to the hardware plane; the replacement is implemented here and had never run on such a set.
- **Codec capability is asserted rather than probed.** Fixed in v0.3.0.

## Corrections to the published note

**The published note quoted the annotated tag object's hash where a reader expects a commit.** `git rev-parse v0.2.0` returns `cf5334a5` — the tag OBJECT — while the commit it points at is `e125b728`. `git log cf5334a5` silently follows through to the commit, so the number looks right until somebody tries to match it against what the release workflow records, which is the commit. The generated half below records the commit. Disambiguate with `git rev-parse v0.2.0^{commit}`.

**`ipk.sha256` records a path rather than a bare filename**, so `sha256sum -c ipk.sha256` fails with "No such file or directory" in the directory a user downloads into. The published note said so and told the reader to compare the hash by hand. Confirmed by `ci/verify-published.sh` in the generated half; fixed from v0.3.0, whose checksum asset carries the bare name.
