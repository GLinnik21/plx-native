## Corrections to the published note

**THIS RELEASE WAS PUBLISHED BY HAND, AND EVERY GATE BUT ONE WAS SKIPPED.** It was cut with `gh release create` from a laptop after a bare tag push. `release.yml`'s `prepare` job is gated on `workflow_dispatch`, and GitHub propagates that skip down the whole `needs` chain — so run 31403652035 ran `tag / version agreement` and nothing else. The gate table in the generated half is that run's own job list: `bump + tag`, `redistributable assets`, `build + verify` and `publish release` all read **skipped**. Every asset's uploader is a person rather than `github-actions[bot]`.

**Three consequences are measurable in the published package, and all three are in the generated half.** All three bundled FFmpeg libraries carry the maintainer's own working directory, because FFmpeg records its whole configure invocation and this build did not happen at CI's fixed path — so the package is not reproducible by anybody, and a reader following our own rebuild instruction could not distinguish "different build directory" from "tampered". The published note was amended to say it was built by hand; this audit is where the evidence for that lives.

**`ipk.sha256` records a path rather than a bare filename**, so `sha256sum -c ipk.sha256` fails with "No such file or directory" in the directory a user downloads into. The published note said so and told the reader to compare the hash by hand. Confirmed by `ci/verify-published.sh` in the generated half; fixed from v0.3.0, whose checksum asset carries the bare name.

**The published note quoted the annotated tag object's hash where a reader expects a commit.** `git rev-parse v0.2.1` returns `d8cf64f6` — the tag OBJECT — while the commit it points at is `8827d32c`. `git log d8cf64f6` silently follows through to the commit, so the number looks right until somebody tries to match it against what the release workflow records, which is the commit. The generated half below records the commit. Disambiguate with `git rev-parse v0.2.1^{commit}`.

**No defect in the app itself is attributable to the hand-publish.** The binary carries no dev-trigger surface, the payload matches v0.2.0's file for file, the version agrees everywhere, and the hash agrees in every place it appears. What was lost was the assurance, not the artifact — and there is no way to tell those apart from the outside, which is the whole argument for the gates.

## Deliberately not done

**The tag was not deleted and the release was not withdrawn.** A hash that has been public has to keep meaning something, and the defects are disclosure problems rather than a compromised binary. v0.3.0 supersedes it eleven days later.
