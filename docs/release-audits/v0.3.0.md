**One line moved, and it is the largest single move in this project's history: video was seen on a television that is not the developer's.** It moved on one person's report of one set running v0.2.1, and it moved exactly that far — 6.5.2 only. webOS 10 stayed where it was, and the two failures in that report were server-side and are not evidence about any television.

## Known issues at release, with provenance

- **Remote-only servers, Plex Relay, servers requiring secure connections, and servers reached by hostname or IPv6.** The app dials a numeric address on the local network and there is nowhere to type one in. Structural.
- **10-bit decoding is still asserted rather than probed**, because the television's codec table has no column for bit depth. Codec and resolution are read from the set as of this release; this one claim is not.
- **On webOS 5 and newer, seeking reloads the stream** rather than moving within it. Slower, and never watched on hardware.

## The safety trigger fired, and where the disclosure was placed

**Two of the three log files were created mode 0644 in the shared `/tmp`.** That is squarely inside the trigger list — "who can read a file the app writes" — so the decision is recorded rather than left implicit.

It is in `Fixed` rather than in a section above the features, by the standard's own mechanical test: **installing the release completes the item.** All three files are 0600 now, including one left behind by an earlier version, so there is nothing for a reader to do and nothing to rotate. The residual is stated in the note itself: the crash log holds a faulting address and a memory map, the stderr log holds whatever an abort prints, neither is known to carry anything about a server or an account, and the event log — which does record the server's name, its address, profile names and episode titles — was already 0600 and is unchanged.
