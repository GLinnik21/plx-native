# Release audit — v0.7.0

The evidence behind [the v0.7.0 release note](https://github.com/GLinnik21/plx-native/blob/main/docs/release-notes/v0.7.0.md). Written for a webosbrew reviewer, a contributor auditing an old release, and us in a year. The section at the bottom is generated from the artifact that was published; everything above it was written by a person before the release ran.

v0.7.0 is the first trunk release since v0.6.0. The 0.6.1–0.6.6 patches were cut from the `release/v0.6` maintenance line; their storage, sign-in and consent work reached `main` in the forward-port [#105](https://github.com/GLinnik21/plx-native/pull/105) (`6f78842e`), and the individual fixes (the k5lp/k3lp Load race and sandbox repair, IPv6 redaction, background presentation) were re-applied to `main` separately. A 0.6.x user upgrading keeps every one of them.

**`pipe_replay_after_eos` was a reproducible regression, found and fixed this cycle.** Tracing it against `235e5199` (2026-09-12) found the DEV replay arm — not the production Up Next handoff, and not user-visible — deciding from the parked route instead of the Up Next handoff; the harness case had gone unexercised against the fixed behaviour (LG checklist item #46) since that commit without anyone noticing, because the regression was confined to the arm the harness itself drives. Fixed on this branch by "dev: the replay-after-EOS arm decides from the Up Next handoff, not the parked route (regression from 235e5199)"; re-run passes twice, all 10 assertions. The pipeline tier's other first-run failure, `pipe_abr_down_staircase`, did not reproduce on a solo re-run — a flake.

**Three of the 32 graded `--server` cases failed; one is a known-carried issue, one was a harness gap this release closed, one is a flake.**

- `seek_transcode` failed once and passed on a solo re-run — a flake.
- `audio_switch_native` failed on harness drift, not app behaviour: #210 made the file's own default track the start pick, so the case's row-0 pick had become a no-op. The case was updated on this branch to pick a genuinely different row; it now passes, and `audio_switch_transcode` (unmodified) continues to pass.
- `subtitle_image_pgs` fails exactly as it did in v0.6.0's audit: every playback assertion passes but no `image cue […]` line ever appears. Unchanged known issue, not investigated further this cycle. The only change on this line since v0.6.0 that could plausibly shift which row the case picks is #167 (external sidecar subtitles added to the Subtitles tab); whether it does was not checked. *Root cause found after this audit (a field report reproduced the same silence on a different library):* the bundled FFmpeg was configured without zlib, so the Matroska demuxer passed mkvmerge's zlib-compressed PGS/VobSub tracks to the decoder still compressed and no display set ever decoded. Fixed in `ci/build-ffmpeg.sh` with a host regression test (`make check-ffmpeg`); that the audited item's track is compressed is inferred, not read, so the case still needs a device re-run.

`offline_play`, `offline_play_v6` and `offline_pick_cached` **SKIPPED**: all three need a real stored sign-in on the debug install, which this pass did not create — this pass made no account writes.

**The third pass's new finding: found, fixed in #245, device-verified on the fourth pass.** After sign-out on 0.7, the app sat on the QR screen and logged this pair about once a second, indefinitely:

```
session: sign-out candidate retirement failed path=/media/internal/.com.beb.plxnative.debug-auth.json unlink_errno=30 neutralize_errno=2
session: queued clear incomplete; retaining revocation and retrying
```

The legacy file does not exist on this install. The jail sees `/media/internal` read-only, and Linux answers `unlink` there with EROFS before it looks the name up, so the absent candidate was read as a survivor and the clear never completed. Because credential commits wait behind a pending erase, a sign-in after that sign-out was not persisted either. [#245](https://github.com/GLinnik21/plx-native/pull/245) fixed it and the fourth pass verified the fix on the TV; see the account of #245 below. The same read-only mount made Delete all local data report absent files as leftovers, fixed by [#246](https://github.com/GLinnik21/plx-native/pull/246).

Trailers are new on this line, so only 0.7.0 nightlies could have sent such reports. Host-verified with tests watched red then green. **Device-verified by the owner** on a debug build of `676e5cea`, 2026-09-25, for the account-menu case above; the item-menu focus cases were not separately exercised on the TV this pass.
- **Sign-out retires an absent candidate behind a read-only mount; a real survivor backs off** ([#245](https://github.com/GLinnik21/plx-native/pull/245), `8dcb7f77`). The fix for the third pass's finding above. A candidate now counts as retired when it is removed, neutralized, or proven absent: a refused unlink is followed by a no-follow lookup (`storage::prove_absent_after_refused_unlink`, the rule telemetry's legacy cleanup already used), a neutralize open answering ENOENT is the same proof, and the revocation-marker removal follows the same rule. A name that exists, or cannot be looked at, is still a failure; such a clear stays queued with its revocation retained, but retries back off 1 s, 2 s, 4 s … capped at 30 s instead of every second. Host tests reproduce the device's EROFS through a test-only, directory-scoped unlink fault, including a sign-in after that sign-out being written and Delete all local data reaching its sweep. **Device-verified on the fourth pass** (debug build of `8dcb7f77`): sign-out went straight to the QR screen with no `candidate retirement failed` or `queued clear incomplete` line; DB8 showed a `ClearTenure` commit (an epoch bump); a relaunch logged `boot: no session — starting QR sign-in`; and a QR sign-in followed by a relaunch logged `boot: stored session — who's watching` and `roster refreshed n=3`, so a sign-in after a sign-out now persists.
- **Delete all local data: an absent file behind a read-only mount is not a leftover** ([#246](https://github.com/GLinnik21/plx-native/pull/246), `033746b6`). The sweep's own bare `remove_file` read the same EROFS on absent `/media/internal` files as survivors, so the result screen told the user data might remain. The sweep, the runtime-log sweep and the recording-artifact sweep now use `storage::remove_file_or_prove_absent` (the recording sweep through an injected function, since `ui/` may not name the storage layer; a new zero-hit `check-deps` rule, `uistorage`, holds that). A file that exists behind the refusal is still a leftover; host tests cover both the absent and the present case. **Device-verified on the fourth pass** (debug build of `033746b6`): after a QR sign-in and seating Guest, Settings → Privacy & data → Delete all local data opened its confirmation on Cancel (#242), and Delete ended on "Local data deleted — Credentials, preferences, telemetry and local diagnostics have been removed.", with no `privacy: … could not be removed` line in the log. Before the fix, on `8dcb7f77`, the same action ended on "Signed out, and most local data deleted / Some files could not be removed…" and the log named four absent `/media/internal/.<id>-{lastplace,telemetry,telemetry-spool,telemetry-crashmark}` files with EROFS.

**Second-pass harness results.** `audio_switch_native` failed with `menupick: row 1 already active — no commit`: the server's sticky per-user stream selection had drifted, so the case's pick was a no-op. That is harness state, the same class as the first pass's drift on this case. Four `auto_*` cases skipped because they need a conditioned link. `offline_play`, `offline_play_v6` and `offline_pick_cached` skipped because their precondition checks the legacy `…debug-auth.json` file rather than the DB8 record the app now stores its sign-in in. That is a harness gap, so these three still say nothing about offline boot.

## Deliberately not done

- **No GitHub Security Advisory** for the offline credential cache: it is a design change disclosed in the note, not a defect in a shipped version.
- **Nightly installs poisoned before #219 are not auto-healed.** Nightlies from 2026-09-19 to 2026-09-23 could persist the account holder's per-server token over a seated managed or Home-member profile (the admin gate lost in `235e5199`, restored in `65098517`). No stable release ever carried that regression, and the nightly is a separate app id (`com.beb.plxnative.nightly`), so a stable 0.6.x → 0.7.0 upgrade cannot inherit it. A heal was tried and dropped because it cannot tell a poisoned record from a Home member legitimately signed in with their own account; the recovery is switching profile away and back.
- **No downgrade path.** A 0.7 record read by a 0.6 build is not supported, and the note says so.
- **`docs/known-issues.md`'s single entry was not rewritten here.** It still describes the k5lp Load-race fix as possibly missing from `main`; the fix is present on this tree (`src/starfish.c`'s `LOAD_RETURNED` gate and `webos.rs`'s `rtkmem` probe). Left for a docs change, not a release document.
