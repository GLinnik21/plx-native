## What this release contains

- **Issue #76 persistence recovery.** Host tests cover fresh reauthentication over a recognized secure envelope whose key service is unavailable, plus the separate client-ID-only primary/plaintext shadow case. Fresh reauthentication takes the explicit owner-only recovery path at the selected candidate and sweeps known lower copies; a selected unknown-format envelope remains blocked, while unused unknown-format copies are preserved. Real keymanager3 behavior remains unconfirmed.
- **`session::save` reports what it actually did, not a bare bool.** `PersistOutcome` (`persisted_plaintext` / `persisted_sealed` / `preserved_existing_secure` with a reason of `not_proven`, `refused_marker_no_fresh_sign_in` or `seal_failed` / `blocked_unknown_envelope` / `write_failed` / `serialization_failed`) replaces the bool `save` used to return. Auth uses `.persisted()` to distinguish a saved session from a run-only session requiring a warning. One `session: persist outcome=<wire>[ reason=<wire>]` log line per save, whichever branch ran, distinguishes deliberate preservation from a genuine write failure.
- **`read_locked` records why each candidate path was rejected, not only that the launch as a whole failed.** `ReadRejection` includes `unparsable` for readable bytes with no recognized shape, and each `CandidateRead` is tagged by its position in the candidate search order (`developer` / `internal` / `app_dir` / `runtime` / `other`), never by exposing a path. The result is a bounded comma-joined wire line and one load log; no trust-policy change is intended.
- **Storage diagnostics are available without successful sign-in or persistent telemetry consent.** The automatic `SignInNotPersisted` report retains the consent-gated defer/replay path. Explicit one-off reports additionally carry owned cold-read errors and eligibility facts, fresh-save errors/readback, and typed per-candidate write attempts with numeric OS errors or durability warnings. Cold evidence is not replaced by a later successful save. Details uses the shared `Popover`/`TableView` and a Send report confirmation; manual requests have a distinct diagnostic source/fingerprint rather than inventing a failed Plex connection. The report's ephemeral event ID and delivery status are shown without creating a persistent user identifier.
- **An unwritable report queue is not the only delivery path.** One-off reports use the ordinary spool when possible and otherwise attempt a bounded background send of the same record. The UI distinguishes queue acceptance from direct sending, successful server response and failure; standing Errors/Usage routing remains unchanged. Notice revision is now 5, while both standing scopes remain 6. Each explicit report asks through its own updated confirmation; no account-wide re-prompt is introduced.
- **Failed fresh saves hold the auth handoff for an explicit decision.** Discovery and final-save warnings have attempt/generation keys; Details can report before a later save replaces that evidence. Continue finalizes from the latest coherent controller state without another write. Host regressions cover real write refusal, stale acknowledgement/report keys, and coherent handoff after reconciliation; native synthetic captures cover presentation, Details, confirmation and Continue.
- **The report and screen wiring has host and receiver evidence.** Save outcomes, one-off fields, and the Details read-out have production call-site tests. Candidate summaries now travel on load-owned detached reports through `telemetry::storage::report_error_with_candidate_reads`, so a probe report cannot steal the session-read summary. A native one-off reached development Sentry with cold storage errors and hardware/webOS context while its selected spool path was deliberately unwritable and standing consent remained off.

## Known issues at release, with provenance

- **Whether a real `keymanager3` recovers the fixed loop the same way the fake one does is unconfirmed.** The dev fake reproduced a matching symptom and host tests covered the recovery; no television with a real key service has run this exact fix.
- **Receiver coverage is partial.** Development Sentry received native event `4175abcfc8948826378a90b3302e1650` through the direct unwritable-spool fallback, including cold candidate/error/eligibility and hardware/webOS facts. Fresh-save arrays were empty in that cold-read experiment; their serialization and real failed-write snapshot coverage is host-side. This build's production endpoint was not exercised. Neither receiver receipts nor PostHog analytics establish real-keymanager3 recovery.
- Every known issue in [v0.6.3's audit](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/release-audits/v0.6.3.md#known-issues-at-release-with-provenance) not superseded above is unchanged, including the one-off libmali SIGSEGV recorded there.
