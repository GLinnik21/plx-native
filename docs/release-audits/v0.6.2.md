## What this release contains

One fix, from two reports that turned out to be the same bug, and the telemetry that would have seen it.

- **Issues #75 and #76 — the sign-in did not persist on 2024 and newer LG sets.** `plex::session::save` seals the session through `com.webos.service.keymanager3` on firmware that has it (2024 and newer sets), and `peek` re-read and re-decrypted the file on every account-menu open; on both reporting sets the service sealed the session but could not open it again, so every read landed `Locked`, the chip said "Sign in", `update` refused, the next launch showed the QR code, and the next save re-sealed into the same unopenable envelope. The sign-in screen's slowness and its "try again" loop are the same failure seen from the discovery stage, which waits on the key service's 4 s LS2 budgets. The dev set (webOS 4.10) has no keymanager3, so this path had never round-tripped on hardware. The fix: `keymanager` proves the round trip before returning a `Sealed`, logs every service refusal once (never the reply text on the calls whose request carries the IV or the payload), drops the undocumented `mac_length` parameter, and classifies an unanswered call (`no_reply`, `unreachable`) and the hub's "Service does not exist" reply (the service's absence) as distinct from a refusal; `session` keeps one in-process copy, treats an unopenable envelope as `LOCKED_RECOVERABLE` for the process, replaces it with the 0600 plaintext file after a fresh sign-in, and persists a `<id>-secure-storage.refused` marker (0600, naming the failing stage) that keeps the install on the plaintext file until sign-out or erase. Reads are never gated on the marker and an ordinary `update()` never converts a present envelope.
- **Storage telemetry.** `session_storage` (`none` / `plaintext` / `secure` / `secure_locked` / `secure_refused` / `unknown`) rides on every usage event; a handled `StorageError` Sentry event (standing error-report consent only) carries the failing stage from a closed vocabulary, the service's numeric error code when one was reached, the storage class and whether the marker is present, once per process per stage, sent after the session lock is released; the sign-in report gained the storage class. `PRIVACY.md`, the in-app policy, the sign-in alert's body and both consent previews name every new field. `POLICY_VERSION` moved to 6, so every existing 0.6.x install is asked the reporting question again on first launch, and the Crash stage now shows why it asks again.

## Known issues at release, with provenance

- **The sign-in fix is unconfirmed on any set that has keymanager3.** It is pinned by the host suite against a scripted service and by the dev-set probe above, which can only show what a firmware WITHOUT the service answers. Whether the reporting sets now stay signed in is answerable only there; the note's Help test this release section asks for exactly that.
- **On a set whose key service never answers, the first launch after this update still pays the service's 4 s budget once** before the stored sign-in is treated as locked. Every later launch skips the service entirely because of the persisted marker. Measured nowhere; derived from the code's budgets.
- Every known issue carried in [v0.6.1's audit](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/release-audits/v0.6.1.md#known-issues-at-release-with-provenance) is unchanged by this release; none of it was re-measured this cycle.

## Deliberately not done

- **A television with keymanager3 was not sought out or acquired.** The path was made testable on the host instead (the scripted service client), and the reporters were asked to try the build.
- **The refused marker is written on ANY failure to open an envelope this install wrote, including a timeout and a failed registration**, not only on a service reply that refuses. A review argued for the reply-only gate, and a trace under a stalled service showed its cost: no marker, so every later launch re-pays the 4 s budget forever, and no report, so nothing ever says so. The trade accepted is that a healthy set that hiccuped once keeps a 0600 file instead of an envelope until its next sign-out. Older sets have only ever had that file.
- **A `no_reply`/`unreachable` during a seal on an install with no envelope is not reported.** With no envelope on disk it is indistinguishable from an older firmware without the service, and reporting it would have meant one event from every such install.
- **The event log's location was not changed for Developer Mode installs.** The #76 reporter's shell cannot see the app's `/tmp` on webOS 11; whether it can see the app's own directory is unmeasured, and the owner chose not to ask the reporter for more. A devmode-only mirror of the logs in the app directory is a possible later change, not part of this release.
- **The consent re-ask on first launch of 0.6.2 is deliberate.** `POLICY_VERSION` moved from 5 to 6 because the storage facts are newly collected; the same rule and the same cost as 0.6.1's re-ask, with one improvement: the question now states the reason it is asked again.
