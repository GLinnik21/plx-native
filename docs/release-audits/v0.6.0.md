**The one failure: `subtitle_image_pgs`.** Every playback assertion passed (24.0 fps steady, no stalls, no errors over the full 90 s cap) but no `image cue […]` line ever appeared — the client never rendered the PGS bitmap. Investigated by tracing the whole path (`ui/track_menu.rs`'s subtitle selection → `metadata::sub_render_ordinal` → `route::commit_subtitle_selection` → `player::desired_sub_idx`/`push_subtitle_bitmap` → `ff.rs`'s `decode_bitmap_cue`) against `v0.5.0`: **every one of those functions is either untouched or reformatted-only since v0.5.0** — no commit in `v0.5.0..HEAD` changes this code path's logic. The harness case itself (`tests/manifest.json`'s `subtitle_image_pgs`, `tab:1,row:1`) is also unchanged since v0.5.0. This makes a v0.6.0 regression unlikely; the remaining candidates are outside what a static diff can see — the test server's copy of this specific item (rk 1919, gitignored `tests/manifest.local.json`-mapped, so not itself part of this repository's history) or the PGS track simply carrying no cues in the tested 10:00–11:30 window. Not re-run against an actual `v0.5.0` build on this device this cycle. Recorded here as a known gap rather than fixed or waved away; see Known issues below.

**By hand.** The Change-profile PIN fix: entered the unprotected Guest profile, opened Change profile, pressed BACK. Event log read `auth: BACK refused — the Change-profile picker is a root` → `back: root route=profiles phase=Profiles backed_out=false action=Home` → `gohome: SAM accepted in 31ms`, and the capture showed the real LG launcher ribbon sliding over the picker — BACK no longer resumed any profile, protected or not. (The household's own PIN was not used or guessed; the fix is unconditional on `stored_is_protected` in the code, so the unprotected branch is equally diagnostic.) The failure screen: live-armed `/tmp/com.beb.plxnative.debug/plxnative-failtest=stream` during playback and captured "Playback failed / The media stream could not be opened" with the support footer `PlxNative 0.7.0-dev · webOS 4.10.2 · m16p3 · M19_DVB · BOARD_PT_1ST · media_source` (version reads `0.7.0-dev` because this was the developer build used for on-device iteration, not the release artifact — the mechanism is identical either way).

## Known issues at release, with provenance

- **Every server transcode failing on platform release 10.3.1 no longer belongs in the note's Known issues as a present-tense defect, and here is why.** It was measured on a rented LG Cloud Test Lab set on 2026-08-27 (board `k24`/`K24_DVB`, release 10.3.1): the app declared its video sink at the panel maximum regardless of codec, and that television refused an H.264 stream at those dimensions with a resource-allocation error before a frame decoded. A narrow, one-line version of the fix (declare `1920x1080@60` for H.264 instead of `3840x2160@60`) was proven against that same television in the same session and then deliberately reverted, because the lab slot was booked for an unrelated ABR investigation. What actually landed on `main` afterward, in commit `4e377aa8` (2026-09-03), is a generalized, per-session, per-codec-table version of that idea — `engine::sink_envelope` — proven on the maintainer's own webOS 4.10 set (where it fixed a real, separately-measured judder defect: a 4K H.264 24p stream declared at 60 was presented at 13.0 fps, at 24 it held 24.1 fps) but **not re-run on the 10.3.1 hardware the original defect was found on**. `docs/webos10-resource-allocation.md` is explicit about this gap in its own status line. The honest release-note treatment is therefore not "fixed" and not "still broken as before" — it is "the mechanism changed, nobody has re-checked it on that television", which is what the note's Known issues section and Help-test section now say instead of repeating v0.5.0's flat failure claim.
- **Auto has only been exercised in a laboratory** — one television, one server, a link throttled on purpose by `tools/netcond.py`. Unchanged from v0.5.0.
- **Playback on webOS 5, 7, 8, 9 and 11 is unverified.** The app starts there — that is the static matrix, and it is all it says.
- **Remote-only servers behind Plex's relay, and servers requiring an encrypted connection**, are reached but have not been watched end to end. Unchanged from v0.5.0.
- **`maxFrameRate` is now read and applied per codec** (`devcaps::Caps::{h264_row,hevc_row}`), which retires the v0.5.0 known issue that the app ignored it entirely. Not carried forward.
- **PGS/VobSub image subtitles did not render on the one item this release's own `--server` run tested them against** (`subtitle_image_pgs`, rk 1919, measured 2026-09-04). See Device test evidence above for the full investigation — the decode/selection code path is unchanged since v0.5.0, so this reads as a pre-existing gap or test-server data state rather than something this release broke, but it was not confirmed against a v0.5.0 build on this device this cycle and is not claimed fixed. Not carried into the public note: it is narrower than the note's bar (one item, one subtitle class, unresolved whether it is even an app defect), and `subtitle_text_srt` — the other subtitle case — passed cleanly.

## Deliberately not done

- **No GitHub Security Advisory was filed for the Change-profile PIN bypass**, despite this project's own release-notes standard naming a GHSA as the mechanism for a security problem found in already-shipped versions. The maintainer's explicit call for this release: release-note disclosure only. Recorded here rather than silently deviating from the documented policy.
- **The generalized Load-envelope fix (`4e377aa8`) was not re-verified on platform release 10.3.1** — the hardware the original, narrower version of the fix was proven on. See Known issues above. Re-running it needs the same LG Cloud Test Lab access the original measurement used.
- **Issue #63 itself remains unreproduced.** Nobody working on this project owns the reporter's exact television, and no log was ever obtained from it. This release ships the mechanism believed to be the cause and a failure screen that would make the next report diagnostic; it does not close the issue.
- **The single-profile-roster PIN gap is unchanged.** A television whose roster holds only one PIN-protected profile still opens it directly on restart with no PIN prompt, because a roster of one has no picker to fall back to. Documented as residual in the release note's disclosure section rather than fixed here.

**One thing unusual about this build, found while doing the local pre-flight step this same skill asks for.** `Makefile`'s `override export PLX_RELEASE := $(if $(RELEASE),1,)` stacked `override` and `export` on one line. Isolated with a throwaway Makefile against this Mac's GNU Make 3.81 (Apple has not shipped a newer Make since Make 4 relicensed under GPLv3): plain `export VAR := value` and `export VAR ?= value` both reach a child process's environment on this Make, with or without `override` on the assignment — but `override export VAR := value`, override and export stacked on one line, sets the value for make's own expansions and never exports it. That is narrower than a nearby comment (for a different variable, `CARGO_INCREMENTAL`) suggests, and this audit does not extend that correction to a line it did not test. A local `make FLAVOR=stable RELEASE=1 ipk` on this Mac linked a binary whose embedded version string was `plxnative@0.7.0-dev`, not `0.6.0` — caught by `ci/check-package.py`'s existing assertion, not by anything failing to build. Split into `override PLX_RELEASE := …` then `export PLX_RELEASE` on its own line and reverified the same way: a local `RELEASE=1` build now reports `plxnative@0.6.0`. **No published release was ever affected** — `release.yml`'s build job runs on `ubuntu-24.04-arm`, whose GNU Make is version 4 (where the combined form is not a no-op at all), so every prior tag's actual artifact was built correctly, and `PLX_RELEASE` did not exist in the tree before v0.5.0 shipped. This was purely a false pass waiting to happen the next time someone relied on a local Mac build's version string instead of CI's.

**A second build-configuration defect, found by the release run itself rather than by pre-flight.** The first attempt to publish this exact tag failed CI's `build + verify` job at `ci/check-elf.sh`'s build-host-identity scan: `pkg/plxnative`, built with `SYMBOLS=1` (this workflow's build job always sets it), carried the CI runner's own absolute paths — `/home/runner/work/plx-native/plx-native/…` and its NDK sysroot include paths — as literal strings, because GCC's `-g` writes the compilation directory and every `-I`/sysroot path into DWARF (`DW_AT_comp_dir` and friends), and `RUST_REMAP`'s `--remap-path-prefix` is a rustc flag GCC never sees. This is not new to this release — `SYMBOLS=1` and this specific scan both predate v0.6.0 — but this is the first release build that ever combined the two, so it is the first time the gap was exercised. Fixed by adding the GCC-side equivalent, `CFLAGS_REMAP` (`-fdebug-prefix-map`), applied wherever `-g` is: `$(HOME)`, `$(WEBOS_SDK)`, and `$(CURDIR)` (the checkout root itself, added after an independent review caught that the first version of this fix left the checkout's home-relative remainder — worktree name, CI's repo-name-twice segment — still varying build to build). Verified locally against this exact NDK toolchain: the tie-break order matters (a throwaway compile confirmed GCC applies the *last* matching `-fdebug-prefix-map`, same as rustc's `--remap-path-prefix`, not the first or the longest), and with the fix, `strings -a pkg/plxnative` no longer contains any `/Users/` or `/home/` path and a full local `ci/check-elf.sh` run (built with `FLAVOR=stable RELEASE=1 SYMBOLS=1`) passes clean.

**That fix has a known, undecided tradeoff, and this release ships without resolving it.** Remapping `DW_AT_comp_dir` to a synthetic path (`/build`, `/webos-sdk`, `/plxnative`) means it no longer resolves to a real, readable file on whatever machine later runs `sentry-cli debug-files upload --include-sources` against `pkg/plxnative.debug` — confirmed locally: `sentry-cli debug-files bundle-sources` against a binary built this way finds zero files, versus finding real ones when `comp_dir` is left pointing at a directory that genuinely exists. `RUST_REMAP` has had this same property since before v0.5.0 (verified: present in `Makefile` at the `v0.5.0` tag), so C sources joining Rust sources in "not locally resolvable" is not a regression this release introduces on its own axis — but `--include-sources` in `release.yml` is itself new since v0.5.0 (verified: absent from `release.yml` at the `v0.5.0` tag) and had never actually run in a published release before this one. Whether Sentry's ingest or `sentry-cli` itself treats an empty source bundle as fatal to the upload, versus a silent degrade to file+line-only symbolication with no inline source snippet, was **not** determined before shipping — reproducing it needs a real `SENTRY_AUTH_TOKEN`, which this audit does not have and would not use for a throwaway local test even if it did. If the upload step fails on it, that surfaces as a release failure on the next run and gets fixed then; if it silently degrades, C crash frames in Sentry lose inline source context (file+line still resolve correctly either way) until a CI-side fix — a real directory or symlink at each remapped path, created between the build and the upload step, the standard workaround for this exact `--remap-path-prefix` + source-bundling interaction — lands in a later change.
