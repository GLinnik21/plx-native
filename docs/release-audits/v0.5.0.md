**What is not established.** No per-case result for this release is recorded anywhere a command can read, so the suite counts above are what the manifest defines rather than what a run reported. That gap is the reason `## Device test evidence` is a required authored section from v0.6.0 on: it is the only claim in a release that grades whether video plays, and it was the one claim living solely in a sentence.

The manifest shows **2** of the 27 server cases declaring a `link_profile`, which is the mechanism that conditions the link through `tools/netcond.py`. The 19-case ABR tier the note describes is therefore not the same set as the `link_profile` cases, and which cases composed it is not recoverable from the tree.

## Known issues at release, with provenance

- **Every server transcode fails on platform release 10.3.1** — which means Auto and the five fixed qualities, leaving only Original. Measured on a **rented** set on 2026-08-27: the app declares its video sink at the panel maximum whatever the codec, and that television refuses an H.264 stream at those dimensions with a resource-allocation error before a frame is decoded. HEVC at the same ceiling plays, which is the control that makes it a codec-specific refusal rather than a bandwidth one. Direct play of an HEVC file is unaffected. Full account: [`docs/webos10-resource-allocation.md`](https://github.com/GLinnik21/plx-native/blob/main/docs/webos10-resource-allocation.md).
- **Auto has been exercised only in a laboratory** — one television, one server, a link throttled on purpose by `tools/netcond.py`. The behaviours it is designed for (a link that degrades slowly, a server already transcoding for someone else) have not been observed anywhere else.
- **Playback on webOS 5, 7, 8, 9 and 11 is unverified.** The app starts there — that is the static matrix, and it is all it says. Nobody has reported watching anything.
- **Remote-only servers behind Plex's relay, and servers requiring an encrypted connection**, are reached but have not been watched end to end.
- **The app ignores `maxFrameRate` in the television's own codec table** (`devcaps.rs` reads the table but not that field), so the profile sent to the server bounds no frame rate and a set that decodes 4K only at 30 fps is told nothing about it.

## Deliberately not done

- **The one-line change that would have avoided the 10.3.1 refusal was proven and not taken.** `docs/webos10-resource-allocation.md` records both the change and the reasoning. It is stated here so that a reviewer meets it in the audit rather than discovering it.
- **`requiredMemory` stays at 160 MB** against a 152 MiB measured peak. It was 60 for two releases, which was below the 120 MB webOS substitutes for an app that declares nothing.
- **No reproducibility claim across machines.** Two builds of this commit on one machine are byte-identical; the bundled FFmpeg records the toolchain paths it was built against, which the generated half quotes in full. The note says so rather than claiming more.
