## Compatibility tiers, and what moved

| Tier | Firmware | Evidence |
|---|---|---|
| Plays video, verified | 2019 LG sets (platform release 4.10) | A human watching the dev set |
| Starts | webOS 4.4.2 up to but not including 5.0 | The static matrix below: **OK on exactly two of the fourteen firmware images**, 4.4.2 and 4.10.0 |
| Does not start | webOS 5.0 and newer, and 3.9.2 and older | The same matrix |

**The ceiling is visible in the linkage and is the whole story of this release.** The generated half records **21 `DT_NEEDED` entries** — this binary links `libAcbAPI` and FFmpeg by name, and those names exist only on webOS 4.x. A `DT_NEEDED` entry is a hard requirement for one exact name, so the loader kills the process before `main` on anything newer. That is why the package declares `webosRelease: '>=4.0, <5.0'`, and why v0.2.0 — which resolves both families at run time instead — drops to 15 entries and passes nine images.

## Known issues at release, with provenance

- **Does not start on webOS 5.0 and newer.** Static, from the matrix below.
- **Codec capability is asserted rather than probed** — the app claims HEVC, 4K and 10-bit because the developer's television can. Fixed in v0.3.0 by reading the television's own codec table.
- **Playback behaviour depends on the firmware**, because media is read through the television's own FFmpeg and its component list cannot be determined from outside. Fixed in v0.2.0 by bundling.

## Corrections to the published note

**The published note quoted the annotated tag object's hash where a reader expects a commit.** `git rev-parse v0.1.0` returns `a68a6328` — the tag OBJECT — while the commit it points at is `d3823f5c`. `git log a68a6328` silently follows through to the commit, so the number looks right until somebody tries to match it against what the release workflow records, which is the commit. The generated half below records the commit. Disambiguate with `git rev-parse v0.1.0^{commit}`.

**`ipk.sha256` records a path rather than a bare filename**, so `sha256sum -c ipk.sha256` fails with "No such file or directory" in the directory a user downloads into. The published note said so and told the reader to compare the hash by hand. Confirmed by `ci/verify-published.sh` in the generated half; fixed from v0.3.0, whose checksum asset carries the bare name.
