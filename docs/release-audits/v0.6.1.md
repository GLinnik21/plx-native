## What this release contains

Two independent fixes, from two different reports.

- **Issue #74 — a playback crash at the start of any video**, on an LG 43UM7400 (2019, Realtek `k5lp` chassis). Covered end to end below (Device test evidence, External compatibility reports, Known issues).
- **Issue #75 — a sign-in screen that gave no reason when it could not reach plex.tv**, reported on a 2024 LG OLED with no log and no telemetry. `net.rs` now records the outcome of the last call to the plex.tv host; `auth.rs` turns that into a bounded, identifier-free sentence (`link_detail`) covering consecutive unanswered polls, elapsed time and the last outcome; `ui/login.rs` shows that sentence and a permanent build/webOS-line/set footer on every sign-in read-out. A failed or stuck sign-in can now be reported: automatically, as a handled `SignInError` Sentry event, when crash-report consent is already on; otherwise through a one-off "Send report" decision alert (`queue::Category::OneOff`) that sends a single identifier-free event, can be declined, and is exempt from the account-wide consent switches by design. `diag` defers the sign-in analytics events while consent is unanswered and replays or drops them once it is answered. `PRIVACY.md`'s `POLICY_VERSION` moved to 5 for this addition, so every existing 0.6.x install is asked the reporting question again on first launch of 0.6.1. See Device test evidence and External compatibility reports below for what has and has not been verified.

**What was verified, and what was not, stated plainly rather than blurred together.** The host suite for the final tree ran clean: `make check` — 2110 default-feature tests and 2139 hostsim tests, 0 failed — plus `CARGO_INCREMENTAL=0 cargo +nightly check --no-default-features`, clean. P1a's new in-flight-dispatch regression test was watched RED against the unfixed v0.6.0 gate first (`left: 51, right: 0` — 51 seam dispatches landed while Load was still in flight, the first of them the `isLoadCompleted` poll) and GREEN after the fix, per this project's reproduce-before-fixing rule. A fw-compat review found `tools/fwcompat.py` OK on every release from 4.4.2 through 11.2.0, and `ci/check-elf.sh` clean with `DT_NEEDED` unchanged at 15 entries. `make FLAVOR=stable RELEASE=1 ipk` followed by `python3 ci/check-package.py` passed every assertion locally.

**A device run did happen this cycle, on 2026-09-10, on the maintainer's own dev set** — the LG 49SM9000PLA above, debug-flavour install, panel off, under the TV lock. Three synthetic pipeline-tier cases passed: `pipe_h264_ac3_1080p` (19 s), `pipe_abr_steady_modest_link` (the full 75 s cap; its segmented HLS is the priming path the fix targets) and `pipe_seek_inplace`. Two server-tier cases passed against a real PMS: `transcode_av1_no_dp_audio` (a real HLS transcode — the reporter's own route into the crash) and `seek_transcode` (a fresh Load on seek). Every log from this run shows the new ordering the fix installs — `native: loadCompleted while Load in flight — deferring` → `SMP: Load returned ok=1` → `native: Load returned after Nms` → `SMP loadCompleted` → Play (or priming) → first feed → `SMP ACB bound` — and the measured in-flight window on this chassis was 874 ms for direct play, 359 ms for segmented HLS and 176 ms for the PMS transcode: the race P1a's gate closes is real on this board too, not only on the reporter's. `devjail: soc=m16p3 rtkmem=n/a` was logged on every boot, as expected on a non-Realtek board.

**The set this team has physical access to is a different board from the reporter's, and this run answers a correspondingly narrower question.** `m16p3` does not have `/dev/rtkmem` missing from its jail and cannot exercise P1b's guard at all — every boot simply logged `devjail: soc=m16p3 rtkmem=n/a` and moved on. This run confirms P1a's sequencing gate does not regress ordinary playback on real hardware, across direct play, segmented HLS and a server transcode; it says nothing about whether P1b's k5lp/k3lp guard, or the underlying crash it works around, is actually fixed on the chassis that reported it. These are two different claims and this audit does not conflate them: **P1a is device-confirmed on the m16p3 set; P1b is not, on any hardware this team holds — its `missing` branch has never been exercised, only its `n/a` branch.** The reporter's own set remains the only place P1b can be confirmed; what to look for there is a `devjail:` line naming a `k5lp`/`k3lp` SoC with `rtkmem=missing`, and whether `SMP: Load returned` now appears within the 20 s budget where issue #74's own log shows it never arriving. The by-hand run with the new `plxnative-holdload` trigger was also done on the `m16p3` set the same day: the pump logged its `deferring` line while the flag was held, the 20 s budget expired into `load_failed`, and the failure read-out was drawn on the panel (`docs/measurements/issue-74-holdload-readout-tv-2026-09-10.png`) — which exercises D.1's budget and read-out path on real hardware without needing the affected chassis.

**The sign-in change (issue #75) was looked at on the dev set on 2026-09-10, after the host suite and the desktop simulator.** With `plxnative-signinfail=error` armed the `m16p3` set drew the failed read-out — the "Couldn’t sign in" heading, the error sentence, the Try again button, the new reachability line (`plex.tv is not answering — couldn't resolve host (curl 6), 1 try, 3 s`) and the new version/firmware footer — and, over it, the "Send a report about this sign-in problem?" alert with its full disclosure text and both buttons. LG's rasterization of every new line is clean at glyph size and the alert's layout over the sign-in route holds on real hardware (`docs/measurements/issue-75-signin-alert-tv-2026-09-10.png`, `docs/measurements/issue-75-signin-readout-tv-2026-09-10.png`). This is a look at the screen, not a reproduction of the report: the dev set reaches plex.tv, so the failure was injected by the dev trigger, and nothing here says the reporter's 2024 OLED now signs in.

## External compatibility reports known at release time

Reporter evidence was available for this release. [GitHub issue #74](https://github.com/GLinnik21/plx-native/issues/74) carries three attached logs from the failing set — `plxnative-events.log`, `plxnative-crash.log` and `plxnative-stderr.log` — plus a Sentry event (`PLX-NATIVE-E`) from a later attempt. The attached logs show a SIGSEGV in libc with `r0=0`, occurring immediately after `SMP loadCompleted (priming before Play)` with no `SMP: Load returned` line ever appearing — exactly the in-flight race P1a's sequencing gate closes. The Sentry event is a different failure mode from a later attempt on the same set: a SIGABRT on the firmware's `OMX_VideoComp` thread, with the main thread inside `StarfishMediaAPIs::Play` at `pump.rs:1096` and the load thread still inside `Load`, at `gst_dvo_context_start` → `DirectVoInit` → `DirectVoRelease`, both blocked in `pthread_mutex_lock`. The set reports platform release 4.10.0 (codename `goldilocks2-grampians`, api `4.1.0`), board `K5LP_DVB`, model `k5lp` — LG's own settings screen shows it as software version `05.40.20` — installed under `/media/developer` (Developer Mode). No firmware tier moves on this report: it is recorded here as the origin and reproduction evidence for the fix, not as a compatibility confirmation, since the fix itself has not been run on this reporter's own hardware. Neither the reporter nor any host is named here, per this project's third-party-data rule.

[GitHub issue #75](https://github.com/GLinnik21/plx-native/issues/75) is a 2024 LG OLED that could not sign in with a PIN, with no log and no telemetry attached — the sign-in screen gave the reporter nothing to go on, and the app had nothing to send even if it had. The dev-set flow itself works on webOS 10.3.1 (the lab's K24 chassis), so the reporter's failure is most likely a plex.tv reachability problem the old screen could not distinguish from "you have not scanned yet". This report is recorded here as the motivation for the change — the reason the screen now says why plex.tv is not answering and the reason a failed sign-in can be reported — not as a compatibility confirmation of any kind: the fix has not been run on the reporter's own set, and no firmware tier moves on it.

## Known issues at release, with provenance

- **P1b's k5lp/k3lp jail guard is unverified on the chassis it targets.** It is built from community-tier evidence — [webosbrew/webos-homebrew-channel PR #202](https://github.com/webosbrew/webos-homebrew-channel/pull/202) and ss4s's own `/dev/rtkmem` detection — not a vendor statement, and this team holds no `k5lp`/`k3lp` hardware to confirm it against. See Device test evidence above.
- **P1a's sequencing gate has host-suite coverage (RED then GREEN, per the fix's own commit) and has now been run on the m16p3 dev set (2026-09-10):** five cases across both harness tiers passed, the new dispatch-deferral ordering appears in every log, and `presented_rate` stayed healthy throughout. The race it closes is general — it does not depend on chassis — so this confirms P1a does not regress ordinary playback; it says nothing about P1b, which this board cannot exercise.
- Every known issue carried in [v0.6.0's audit](https://github.com/GLinnik21/plx-native/blob/main/docs/release-audits/v0.6.0.md#known-issues-at-release-with-provenance) is unchanged by this release; none of it was re-measured this cycle.
- **The sign-in reachability fix (issue #75) is unconfirmed against the reporting set.** Its screens were looked at on the dev television (see Device test evidence) with the failure injected by a dev trigger, which proves the rendering and the alert's layout on real hardware and nothing about the reporter's network. The reporter's own set — a 2024 LG OLED — is unavailable to this team, so whether that set now signs in, or now sends a usable report, is only answerable there.

## Deliberately not done

- **P1b was not, and could not be, confirmed on real hardware for this release.** A device run did happen on 2026-09-10 (see Device test evidence), but only on a board this team holds that is not `k5lp`/`k3lp` — its `rtkmem=missing` branch has never been exercised on any hardware here. Confirming it needs the reporter's own chassis or one like it. The deferral-and-budget path itself WAS exercised by hand on the same set the same day, with the new `plxnative-holdload` trigger holding the Load-returned flag for 30 s under a `plxnative-playurl` direct-play clip: the log read `native: loadCompleted while Load in flight — deferring` → `SMP: Load returned ok=1` → `holdload: armed — holding the Load-returned flag for 30000ms` → `native: Load did not return within 20s — publishing load_failed` → (no Play, no feed) → `native: Load returned after 30255ms`, and the panel capture showed the full-screen failure read-out ("Playback failed — This TV could not start the video stream", footer `PlxNative 0.6.2-dev · webOS 4.10.2 · m16p3 · … · tv_pipeline`) rather than a spinner — the capture is [docs/measurements/issue-74-holdload-readout-tv-2026-09-10.png](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/measurements/issue-74-holdload-readout-tv-2026-09-10.png). That proves the budget lands on the read-out on real hardware; it says nothing about why Load would take that long on a k5lp.
- **The reporter's exact set was not sought out or acquired.** Confirming P1b against the actual failure requires `k5lp`/`k3lp` hardware this team does not have; buying or borrowing one was out of scope for this release.
- **Issue #75's reporting set was likewise not sought out or acquired**; the fix was reproduced red-then-green on the host suite and the simulator, and its screens were given one injected-failure look on the dev set rather than a real unreachable-plex.tv run, which would have meant cutting the household's uplink for a screen the trigger already reaches.
- **The consent re-ask on first launch of 0.6.1 is deliberate, not a side effect.** `POLICY_VERSION` moved from 4 to 5 because the sign-in report is a newly-collected event this project's own rule (`telemetry/consent.rs`) requires a bump for: a bump asks every existing install again rather than silently extending a previous answer to cover a form of collection it was never asked about. It costs every returning user one more screen on their next launch; that cost was accepted rather than worked around.
- **Four files sit outside every package's declared file-ownership list, and were left there rather than reverted.** `rust-modules/src/plex/identity.rs` (making `version_is_the_package_or_the_next_minor_dev` line-aware, so it does not fail once `RELEASE_LINE` exists), `rust-modules/src/lib.rs` and the new `rust-modules/src/release_line.rs` (the version-derivation helpers moved into the crate so a host unit test could exercise them, per P2's own requirement), and `rust-modules/src/app.rs` (the `crate::player::clear_jail_refusal_for_route_exit()` call added to `exit_player`, so a jail refusal retires when the viewer leaves the player route instead of latching `PlaybackState::Error` onto every later screen) are all necessary consequences of a required fix rather than opportunistic changes, so undoing them to fit the ownership list would either reintroduce the bug the fix closes or remove the coverage the spec asked for. Recorded here rather than reverted.
