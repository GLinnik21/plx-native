## What this release contains

- **Issue #76, second attempt.** v0.6.2's fix trusted a keymanager3 envelope after an in-process round trip and armed its persisted refused marker only after a launch had already found a locked envelope. Six reporters (platform releases 5.6.2, 9.2.2, 10.3.1 and three at 11.2.0) showed that on their sets the in-process check passes and the next launch cannot open the envelope, so a clean first read sealed the sign-in and the relaunch asked again; three further ways the marker failed to arm and a report path that dropped the very report the reporters switched on were found by tracing the 0.6.2 tag with six host tests watched red. The fix: sealed storage is earned by a cross-launch probe (`<id>-secure-probe.json` sealed beside the plaintext session; a later launch that opens it writes `<id>-secure-storage.proven`, a failure writes `<id>-secure-storage.refused` with the failing stage; stalls and unreachable services retry a bounded number of times — `UNAVAILABLE_MAX_LAUNCHES = 3` — before being graded refused); every read a key manager actually ANSWERED and refused arms the marker; a read that got no answer at all, or that could not obtain the identity it needed, is transient instead and leaves the marker untouched (the next bullet); an unrecoverable-but-ours envelope is replaced by a fresh sign-in; a failed persist publishes the in-process session and reports `write_failed`; the storage report cannot be marked reported before it was sent or deferred; an install upgraded with a working envelope is promoted on its first successful read. `keymanager` records every silent failure path as a stage (a refusal without a code, an undecodable output, a non-UTF-8 input with the handle aborted, a legacy-backend envelope).
- **A key service that stops answering AFTER it has already sealed a sign-in no longer costs that sign-in.** Split from the first read failure above once it was clear the two need different accounting: `open_failure_is_transient` grades a failure that never reached a key manager (a budget timeout, a registration that never reached the bus, the hub's own `-1` "Service does not exist") as `LOCKED_UNAVAILABLE` rather than a refusal — the envelope is left byte-identical, no refused marker is written, and the launch reports `secure_unavailable`. It settles rather than retrying forever, counted in a small `secure-storage.unavailable` launch counter cleared the moment one launch reads the file, bounded by the same `UNAVAILABLE_MAX_LAUNCHES`. The sign-in screen offers **Try again** over this state (`ui::login`'s storage read-out, its `ActionRow`-driven focus pop, its room-derived note budget, and — after five review-finding fixes — a press that actually dips on OK-down and commits on OK-up, gates a stale worker result against the attempt and phase still on screen, calls the same roster refresh the boot gate's own stored-session path does, and — landed last, the same shape of bug as the others — claims the worker slot from EITHER settled state rather than `RETRY_IDLE` alone, so a press after a failed retry asks again instead of doing nothing for the rest of the visit). **Verified on the maintainer's television** (`docs/measurements/ls2-identity-tv-2026-09-10.md` §10.4, using the dev-only fake key service to stand in for a stalled real one, since this set has none): the envelope stayed byte-identical across the stalled launch, no refused marker was written, the unavailable counter read `{"launches":1,"stage":"no_reply"}`, the storage report reached Sentry as `StorageError: no_reply` with `sealed_identity: "anonymous"`, and a Try again press logged `keymanager: retry -> no_reply` and changed none of the four disk facts — one press only; the same session's measurement doc originally implied a repeated press had also been exercised there and was corrected to say only one was (see the measurements note below). The escalation to a permanent refusal after three such launches, and a Try again that actually succeeds, are exercised only on the simulator (`docs/measurements/keymanager-unavailable-signin-sim-2026-09-10.md`) — `dev::keymanager_fake_mode` is read once at boot, so a fake armed `stall` cannot start answering mid-launch, and the device session only ran one stalled launch before handing the set back.
- **The LS2 identity ladder gained a second stable shape, and the story behind it was corrected twice.** LG's key manager keys ownership by the caller's LS2 identity — the application id when the hub supplies one, else the sender's service name (decompiled from the v1 `keymanager` on the dev set). This app now asks in three shapes, preferred in order: an application-service registration under its own app id (`Identity::AppId`), a plain named registration under the same app id (`Identity::Named`, new this release), and an anonymous registration (`Identity::Anonymous`, the only shape every earlier build ever used and a different owner on every launch — the working root cause of "sealed on Monday, cannot be opened on Tuesday"). The identity is pinned to the file it seals rather than re-decided per launch, recorded in the envelope, the probe and the proven marker; an identity a launch cannot obtain is the transient `identity_unavailable` stage, which never arms the cross-launch refused marker, because nothing was learned about the key, only about a name. **Both named shapes are gated behind the same check**, `player::acb_holds_app_id()`: on webOS 4, `libAcbAPI` holds the app id as a bus name for the life of the process, so claiming it for the key manager would cost a picture to save a sign-in, and the gate short-circuits before the hub is asked anything at all — settling `anonymous` without a registration attempt. webOS 5.0 deleted `libAcbAPI` outright, so any set without it (webOS 5 and newer) reaches the gate open. This section originally attributed the dev set's refusal of the application-service form to `-1028 Attempted to register for a service name that already exists`, read through a probe that ran *after* ACB had already registered; measured again at BOOT, before anything of ours had registered, the same set answers **`-1027 Invalid permissions`** for the app id and for no name at all, which cannot be a name-taken verdict and instead reads as a verdict on the registration method — and that is what put the named shape, `LSRegister(app_id)`, on the list, since the dev-mode role file's `allowedNames` grants plain `LSRegister` even where it refuses the application-service form. **Measured on the dev set: the hub grants the named shape** — `ls2probe: plain LSRegister name=appid: registered`, an outbound `getForegroundAppInfo` completed under it, and ACB still initializing exactly once in the same log — so the shape is real rather than assumed, but **it has never sealed anything on any television**, because webOS 4's ACB gate keeps this set on `anonymous` regardless and no set without `libAcbAPI` has been available to reach the gate open. `docs/measurements/ls2-identity-tv-2026-09-10.md` (§§1–9 the first session, §10 a second session the same evening) is the full record; `LSRegisterPubPriv` was considered and rejected on four counts recorded there (undeclared in the NDK sysroot, absent from 11.2.0's `libluna-service2.so.3`, removed upstream in webOS OSE, and redundant with the named shape once there is no pub/priv split left). The storage report now carries `registered_with_name` beside `registered_with_app_id` (two Yes/No facts, never both true, off one latch) and `sealed_identity` — which identity protected the specific file or probe the report is about, distinct from what this launch registered as, because the whole question issue #76 asks is whether the two differ. **The ACB gate applies to the OPEN side too, not only to deciding what to seal under** (review finding, `keymanager::acb_withholds_required_identity`): opening an envelope recorded as `app_id` or `named` used to go straight to the hub for that exact bus name, and the hub GRANTING it is the bad outcome on a set whose ACB is about to want the same name, since winning that race costs the television its video plane to save a sign-in — it now refuses before asking, transiently (`IdentityUnavailable`, envelope kept, no refused marker). And a process that walks down the ladder more than once in a launch (`app_id` → `named` → `anonymous`, a hub that revokes one shape at a time) used to log only the first step, because every downgrade shared one dedup key; the key is now `<key>:<identity>`, so the step that actually leaves the process with no stable owner — the one a reporter's log has to carry — is no longer swallowed by the first one's line.
- **Consent scope model.** A privacy-notice revision never re-asks; per-category scope versions (`ERRORS_SCOPE`, `USAGE_SCOPE`, both still 6) replace the single policy version; the stored decision records the scope each category accepted and never rewrites it; an update asks only categories that are on and below the current scope; a stored No is never re-asked; declining an expansion keeps the accepted scope and is not asked again until the scope grows further; events above the accepted scope are withheld, not sent with placeholders; a storage report found before the question is answered is deferred in memory for that launch. `sealed_identity` and `registered_with_name` fit inside the standing scope 6 purpose ("how your sign-in is stored") rather than widening it, so they landed as a `NOTICE_REVISION` bump (now 3) rather than a new question. Migration of every stored shape 0.6.0–0.6.2 wrote is tested.
- **Owned-file trust, in two layers.** The first layer repairs an owned file's mode: every app-owned file under `/media/developer` — the session file, the telemetry decision file and spool, both markers, the probe, the crash-mark file, the panic-log writer and the dev-only fake-keymanager key file — repairs a widened mode back to 0600 via `fchmod` on the already-open, ownership-checked fd (`session::repair_owned_mode`) instead of refusing to read or append to it, closing the silent-outage path the 0777 spool finding below exposed. A standing grep-gate test, `every_file_creation_in_telemetry_and_session_names_mode_0600`, walks `telemetry/` and `plex/session.rs` and fails if any file-creation call site omits an explicit `.mode(0o600)`; verified to actually catch a regression by injecting an unmoded `File::create`, watching the test fail at that line, then removing the probe. **The second layer, landed the same day on review, separates repairing the mode from trusting the content it protected while it was wide open**: `repair_owned_mode` now returns `ModeTrust::Trusted` or `Repaired { readable_only }`, and a widened mode carrying any group/other WRITE bit (not merely read) is never parsed as ours — another uid on the shared namespace could have rewritten it between our last write and this read. A write-widened session file is set aside rather than trusted (see below); a write-widened consent file resets both categories to unanswered and both identifiers are discarded; a write-widened spool is truncated to zero and its in-memory count reset, on both the read/compaction path and the append fast path; a write-widened marker or probe file is ignored and deleted outright. Read-only widening (a group/other read bit alone) stays a disclosure problem only — the content is still trusted and loads as written. Both branches are pinned by discriminating tests (a read-only-widened twin beside every write-widened case).
- **A write-widened SESSION file is quarantined rather than deleted.** The rule is unchanged — bytes another uid could have written are never parsed and must not still be at the name the next launch reads — but what happens to them changed: they are renamed to `<id>-auth.json.untrusted` beside themselves, still 0600, never opened again by anything in the app, and kept as the only record of what was tampered with. Only the most recent quarantine is kept — a later tampering replaces it rather than accumulating a series. `rename` replaces a file or symlink a peer planted and fails on a directory; that failure, **and — review finding, fixed 2026-09-11 — a mode repair that did not itself take** (a read-only remount, a jail that denies `fchmod`), both fall back to the outright delete this branch always did, rather than moving a real account token to a fixed, guessable name that is still writable by the peer that widened it. `ModeTrust::Repaired` now carries whether the `fchmod` actually succeeded, instead of reporting a file as owner-only on the strength of having asked. Sign-out and Delete all local data remove the quarantined copy with the session it belonged to.
- **A foreign envelope at a lower-priority candidate path survives being swept by a save at a higher-priority one** (review finding, fixed 2026-09-11). A successful seal and the plaintext-recovery write both used to clean every OTHER candidate path and delete whatever they found there — including a newer build's envelope, unreadable here and readable again after an upgrade, which is exactly the file `a_foreign_envelope_is_never_overwritten_by_a_proven_installs_seal` already protects one branch earlier. The two sweeps are now one function, `sweep_other_candidates`, which steps around an unrecognized envelope (still removing every atomic-write sibling, which is ours either way). The guard that decides "is there a foreign envelope here" read through the trust-blind path, too, so a planted, world-writable plaintext candidate could answer "nothing foreign here" and unblock the very save whose sweep then destroyed the real envelope beneath it; it now reads through the trust-checked path and skips an untrusted candidate rather than letting it decide.
- **A secure envelope this build does not recognize is never written over by anything this build produces, a completed sign-in included** — closing a case the unproven-branch guard already covered for the proven branch: a proven install used to fall straight through to `keymanager::seal` on any unreadable secure file, including a newer build's format it has never read, destroying an envelope that would have opened again after the upgrade. Only `clear()` (sign out, or Delete all local data) removes an unrecognized envelope now.
- **Replay is documented as a known, undetected limitation rather than implied away.** `O_NOFOLLOW` on the final `open(2)` protects only the leaf name; every candidate path passes through `/media/developer` (measured `drwxrwxrwx` root:root, no sticky bit), `/media/internal` (mount flag known, owning uid/gid/mode not independently measured on this device), or this install's own directory (itself inside `/media/developer` on Developer Mode). A peer with rename rights in the shared directory can move this install's own, currently-valid, correctly-owned, correctly-0600 file aside and later move the same, now-stale bytes back — every check this module makes (ownership, regular-file, the trust-vs-repair split above) is powerless against it, because the replayed file really is this install's own. Two tests pin this as expected, not-yet-fixable behavior rather than a bug: `plex::session::tests::a_replayed_older_valid_session_file_is_indistinguishable_from_current` and `telemetry::tests::a_replayed_older_valid_consent_file_is_accepted`. `repair_owned_mode`'s verdict-before-repair ordering (the Trusted/Repaired decision is made from the mode the CALLER snapshotted before invoking it, never from the mode after the fchmod) is separately pinned by its own unit test rather than left to hold only incidentally.
- **Why the sets behave this way (decompiled on the dev set, 2026-09-10).** LG's v1 key manager keys ownership by the caller's LS2 identity — the application id when the hub supplies one, else the sender's service name — and stores keys in SQLite on flash; a live probe showed a key stored without an application id is invisible to the next process. No third-party native app on the set (Netflix, Prime Video, Apple TV, YouTube) uses a key manager; they persist sign-ins in app-private directories. A registration change to the application-service form itself needs a bus name the Developer Mode role permits, which appears to require shipping a service in the package; that is not in this release.
- **Dev-only fake key service** (`plxnative-keymanager=<mode>`, compiled out of release builds) with the modes `perprocess`, `healthy`, `stall`, `refuse=<code>`, `nocode`, `badoutput`, `absent`, so the reporters' failure and the later-stall failure are both scripted scenarios on the simulator and on the debug install.
- **Every 0.6.3 report proved to arrive, from the receiving end.** `docs/measurements/telemetry-proof-tv-2026-09-10.md`: five scenarios driven on the dev television and confirmed in Sentry and PostHog by query, not from the app's own "sent" log line — the one-off and standing sign-in reports, the storage error report, a deliberate SIGSEGV, and a storage report deferred across an unanswered consent question — each preceded by a negative control that produced zero rows in both systems for its window. Found and fixed as part of that session: `signin::event_body` carried no occurrence timestamp (a spooled sign-in report was dated to when it was finally sent, not when it happened — `storage::event_body` already carried one); a flush did not log which spooled records the current consent no longer allowed before dropping them; neither a storage report's stage/outcome nor a deferral was logged at all. All three are fixed — `report_error` now logs one scrub-safe `storage report: stage=<code> class=<code> outcome=<sent|deferred|dropped>` line per call, and `replay_deferred` logs the count and result whenever it actually replays something held from an earlier unanswered-consent launch, closing the exact gap scenario 2 below had to infer around.
- **Credential-storage decompile decision** (`docs/measurements/credential-storage-native-apps-2026-09-10.md`). Decompiled Apple TV, Prime Video, Netflix and YouTube on the dev set: every one of the three that stores a real credential seals it through the SoC secure store (`libdile_crypto.so.0`), each behind its own partner-scoped DILE entry point with no generic third-party write path open to a homebrew app; YouTube/Cobalt stores its cookie jar in the clear, exactly where this app already was before this branch. Decision: keep `keymanager3` as the sealed state rather than add a locally-generated key — a key stored beside the data, or derived from a device serial or LGUDID, secures nothing against a peer process already running as this app's own uid, since both the commercial schemes and ours unwrap the key in-process under that uid regardless. `SECURITY.md` now states the Developer Mode shared-namespace exposure this decompile surfaced explicitly: `/media/developer` is `drwxrwxrwx` root:root, so mode is the entire boundary a file there can draw against a sibling app (a peer can unlink or rename but not read a 0600 file this app owns), and states plainly that a retail install (`jail_native.conf`, `mountappdir`) does not have this exposure at all.
- **Handled events gained the crash path's hardware/webOS context.** `sdk::start` puts the `webos`/`hardware` contexts on the Sentry SDK's own scope, which only a native crash envelope copies from — a handled event this crate serialises by hand (playback, sign-in, storage) never touched that scope and so shipped with no `hardware`/`webos` context at all, seen live in Sentry issue PLX-NATIVE-F (event `097ae1ebb1b4afa5dc8f607e9b28aaa5`). `telemetry::sentry::attach_hardware_context` is the one function all three call sites now share, so a handled event and a crash report read identically in Sentry's Contexts UI; pinned per call site by `handled_playback_error_carries_the_same_hardware_context_as_a_crash`, `handled_signin_error_carries_the_same_hardware_context_as_a_crash` and `handled_storage_error_carries_the_same_hardware_context_as_a_crash`. `PRIVACY.md` names the added fields once per report kind.
- **The "cannot play video on this chassis" read-out no longer promises a Homebrew Channel fix that was reverted before it ever shipped.** `player::jail_error_shape`'s `FailureKind::JailMissingRtkmem` remedy cited webosbrew/webos-homebrew-channel PR #202, merged 2024-12-25 and reverted by PR #211 on 2025-02-26 without landing in any tagged release; a k5lp reporter reinstalled on that advice and still hit the refusal. The condition citation (PR #202 as the community record that the `native_devmode` jail on k5lp/k3lp omits `/dev/rtkmem`) is unchanged and still correct — only the claimed remedy was false. The screen and its log line now say a reinstall does not fix this and name the community's surviving workaround, `mariotaku/kodi.addon.webos-jailer-fix`, as where the community has looked rather than something this project verifies.

## External compatibility reports known at release time

[GitHub issue #76](https://github.com/GLinnik21/plx-native/issues/76) now carries six reporters, all Developer Mode installs, all with the same result on 0.6.2: three at platform release 11.2.0 (an OLED77G45LW, an OLED55G3LA, and a 50NU800B6LC), the OLED55C41LA from the duplicate [#75](https://github.com/GLinnik21/plx-native/issues/75) at 9.2.2, and two further reporters at platform releases 5.6.2 and 10.3.1. **The affected range is webOS 5 through webOS 11** — the earlier note's "2024 and newer" undersold it: 5.6.2 and 6.x-class sets from well before 2024 show the same failure, because the cause is the anonymous LS2 identity rather than any particular model year. Two of the six switched error reports on; nothing arrived, for the reason fixed above. No firmware tier moves on these reports.

## Known issues at release, with provenance

- **Whether the real keymanager3 behaves like the fake is unconfirmed, on both the first-read failure and the later-stall failure.** The fake's per-process key reproduces the reporters' cadence exactly and the decompiled v1 ownership rule explains it, but keymanager3 itself was never exercised. The `key_outcome` field in the first report from a reporter's set answers the first; `sealed_identity` and the `no_reply`/`unreachable` stage codes answer the second.
- **The plain named LS2 identity is proven grantable on the dev set's hub but has never sealed a session on any television.** webOS 4's ACB gate short-circuits before the hub is asked, so `Identity::Named` remains a path no television has executed end to end; nothing here removes the possibility it behaves differently from `Identity::AppId` once it is actually used.
- **The unavailable-launch escalation (three unanswered launches → graded refused) is exercised only on the simulator**, not on hardware — the device session ran one stalled launch before handing the television back. Derived from the code and confirmed in the simulator; not yet watched happen on a set.
- **A stalled key service costs up to one LS2 budget per launch** until the probe attempts are exhausted; derived from the code, not measured.
- **Two files found at 0777 on the dev set** (`com.beb.plxnative.debug-telemetry-spool.bin`, `com.beb.plxnative.debug-telemetry.json`) are not derivable from this repository's own history as something the app wrote — every creation path in `telemetry/spool.rs`, `telemetry/mod.rs`/`consent.rs` and `paths.rs`, from the first telemetry commit through this branch's HEAD, names `0o600` explicitly. The most consistent explanation is an external actor in the shared `/media/developer` namespace (a peer devmode app's own tooling, or a manual `chmod`); the retired `com.glin.plexpoc-auth.json` carries the identical 0777 mode despite its own writer also having named 0600. See `docs/measurements/credential-storage-native-apps-2026-09-10.md`.
- **A television with both a stalled key service AND no route to plex.tv lands on the sign-in flow's own `Couldn't sign in` read-out, not the storage one**, and is never told its saved sign-in is still there. ## Deliberately not done

- **The application-service bus registration was not changed.** It still needs a role the Developer Mode install does not get today; shipping a service to obtain the modern role is a packaging experiment that has not been run on any 9.x/11.x set. A second, more stable shape — a plain named registration under the same app id — was added instead, proven grantable on the dev set's hub, but it has never actually sealed a session anywhere: webOS 4's ACB gate keeps this set on the anonymous identity regardless, and no set without `libAcbAPI` was available to reach the gate open.
- **Forward-port to main** is deferred until the trunk's UI refactor lands (owner decision 2026-09-10).
- **The v0.6.2 re-ask is not undone** for people who already answered it; the new model only stops it from recurring.
