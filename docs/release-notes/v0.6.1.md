# v0.6.1 — a crash at the start of any video, fixed

This release fixes a crash reported on an LG 43UM7400 (2019, Realtek `k5lp` chassis): the app died the moment any video, of any kind, started playing. No action required — this update installs the same way every other one does.

## Fixed

- **Playback no longer crashes at the very start of any video.** Starting a video hands the television's own StarfishMediaAPIs a synchronous Load call, and until that call actually returns there is no decoder object yet for anything else to touch — but the app had no way to tell "the call is still running" from "it has returned", so a second thread could poll or drive that not-yet-ready object in the same window. Two of the ways this was reported to fail are exactly that race: a null-pointer crash on the priming path, and a deadlock between Play and the Load call itself that ends in a decoder-component abort. Every path into the decoder now waits for a signal that the Load call has actually returned before touching it, with a 20-second cutoff that ends in the normal failure screen rather than a stuck spinner if it never does.
- **A specific 2019 chassis is refused cleanly instead of crashing.** On 2019 LG sets built around a Realtek `k5lp` or `k3lp` chip — the reporting set's own board family — LG's own Developer Mode sandbox leaves the app without `/dev/rtkmem`, a device node the television's video path needs, and every native video app installed that way crashes or hangs (Kodi and Moonlight included). The Homebrew Channel carries the fix for it ([webosbrew/webos-homebrew-channel PR #202](https://github.com/webosbrew/webos-homebrew-channel/pull/202)), so on these sets install through the Homebrew Channel rather than through Developer Mode. This is what the homebrew community has found and documented, not something LG has stated, so the app now checks for it once at startup and — only when the check finds the device missing on one of these two chassis families — refuses to start the video rather than letting the television crash. The failure screen names the finding and points at that remedy; the app cannot patch the sandbox itself.

## Changed

- **Opt-in reporting now says which sandbox a set runs in.** If you have switched on usage or error reporting, every report carries two more fixed-vocabulary values beside the chassis it already named: whether the app was installed through Developer Mode or the Homebrew Channel, and whether the `/dev/rtkmem` check above found the device present, missing, or not applicable. Never the install path. A playback that fails because the television's Load call never returned is now reported under its own category, `load_timeout`, instead of the generic pipeline one, and the error trace records how long that call took as a coarse bucket, never a millisecond count. The full list is in [PRIVACY.md](https://github.com/GLinnik21/plx-native/blob/release/v0.6/PRIVACY.md). Nothing is sent unless you opted in.

## Compatibility

- **Plays video, verified by watching it — 2019 LG sets.** One television: an LG 49SM9000PLA, which reports platform release 4.10.2 (LG markets this generation as webOS 4.5).
- **Plays video, reported by someone else — one 2021 set.** [mariotaku](https://github.com/mariotaku) of webosbrew ran v0.2.1 on an LG 65UP7560AUD (platform release 6.5.2) on 2026-08-11 and got a picture: [issue #22](https://github.com/GLinnik21/plx-native/issues/22). Six of eight attempts played. That report has not been repeated on this version.
- **Starts, and nothing further is known — every other firmware from webOS 4.0 up.** The loader resolves this binary's libraries and symbols cleanly against every firmware image webosbrew has at 4.0 or newer. That grades startup and says nothing at all about whether video plays; the matrix is in the [technical audit](https://github.com/GLinnik21/plx-native/blob/main/docs/release-audits/v0.6.0.md).
- **Does not start — webOS 3.9.2 and older.** Symbols the app needs are missing from those firmwares, so the process is killed before anything appears.

If your set is in the middle two groups, [tell us what happened](https://github.com/GLinnik21/plx-native/issues). It working is as useful a report as it failing.

## Installing

Download **com.beb.plxnative_0.6.1_arm.ipk** and install it with the [Homebrew Channel](https://github.com/webosbrew/webos-homebrew-channel) or [dev-manager-desktop](https://github.com/webosbrew/dev-manager-desktop). You do **not** need a rooted TV.

Nothing in this distribution chain is signed, so this sha256 is what tells you the file you have is the file published here:

```
__IPK_SHA256__  com.beb.plxnative_0.6.1_arm.ipk
```

[Installing and checking a download](https://github.com/GLinnik21/plx-native/blob/main/docs/install-and-verify.md) covers the other assets, how to check the hash on each platform, and the Developer Mode expiry that uninstalls your apps. This package bundles FFmpeg under LGPL-2.1-or-later and its complete corresponding source is attached to this release. Exactly what was built, verified and shipped is in the [technical audit for v0.6.1](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/release-audits/v0.6.1.md).
