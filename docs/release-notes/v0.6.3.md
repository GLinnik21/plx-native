# v0.6.3 — the sign-in stays, and the app stops asking twice

0.6.2 did not keep the sign-in after all, on sets across webOS 5 through webOS 11: six owners reported it, and the report they switched on never reached us. This release fixes both, keeps a sealed sign-in in place even if the television's key service goes quiet later, and changes how the app asks about reporting so an update no longer repeats the whole question for everyone. No action required.

## Fixed

- **The sign-in survives a relaunch.** 0.6.2 trusted the television's key service if it could reopen a sealed sign-in within the same run; on the reporters' sets that check passes and the next launch still cannot open it. The app now keeps the sign-in in the plain owner-only file and seals a small test envelope beside it; only a later launch that can reopen that test earns the sealed storage. A test that fails marks the key service as refused on this television and the sign-in stays in the file. Verified end to end with a scripted key service on the simulator and on the maintainer's television, including the exact failure the reporters see. See [issue #76](https://github.com/GLinnik21/plx-native/issues/76).
- **A sealed sign-in survives the key service going quiet LATER, not only at that first check.** If the key service that already sealed your sign-in stops answering on some later launch — a stall, a registration that never reaches the system bus — the sealed file is left exactly as it is. The sign-in screen says so and offers **Try again**; only signing in again would replace what is stored. Verified on the maintainer's television with a scripted key service standing in for a stalled one: the sealed file stayed byte-for-byte unchanged across three launches and a Try again press.
- **A storage failure found before you answer the reporting question is no longer lost.** It is held in memory for that launch and sent once you say yes, or discarded if you say no or close the app.
- **A sign-in that could not be written to disk is reported and named in the log**, instead of showing your account for the run and asking again next time.
- **Error reporting that had gone silent on some televisions starts working again.** Something else on the television — not this app — had widened the permissions on the file the app queues reports in, and the app used to treat that as a reason to stop sending anything at all, forever, with no message. It now repairs that file back to owner-only the next time it is opened, and reporting resumes from there. Confirmed on the maintainer's television by checking the reports actually arrived, not just that the app claimed to send them.
- **The "cannot play video on this chassis" screen no longer tells you a Homebrew Channel reinstall will fix it.** That advice cited a jailer fix that was merged and then reverted before it ever shipped in a tagged Homebrew Channel release, and at least one reporter reinstalled on the strength of it and still hit the refusal. The screen and its log line now say plainly that reinstalling does not help, and point to the community's own surviving workaround instead.

## Changed

- **The reporting question is asked only about what grew, and only if you had it on.** A stored "no" is never asked again by an update. Only the category whose collection actually widened is asked, with one line saying what changed; the other category keeps its answer. Declining the wider collection keeps what you already agreed to and sends nothing new. Turning a category off is still done in Settings. Wording changes to the privacy notice never open the question.
- **A handled error report — sign-in, storage, or a caught playback failure — now carries the same television model, chipset, webOS release and sandbox facts a crash report already did.** Sentry issues built from these reports used to show only the report's own detail and nothing about which television it came from; they now read the same in Sentry's Contexts panel as a native crash does.
- **Storage error reports carry more fixed-vocabulary detail about which system-bus identity protected your sign-in.** Two Yes/No facts say how the television identified itself to the key service on that launch; a third value says which identity actually protected the file the report is about. Together they can tell a key that is simply unavailable apart from one that changed owners between launches — the exact question issue #76 needs answered. The full list is in [PRIVACY.md](https://github.com/GLinnik21/plx-native/blob/release/v0.6/PRIVACY.md). Nothing is sent unless you opted in.
- **A saved sign-in file another app on the television had made writable is no longer silently thrown away.** The app already refused to trust such a file; it now sets it aside under its own name with `.untrusted` on the end, instead of deleting it, so it is still there to look at if you ask about it. Signing out, or Delete all local data, removes it along with everything else.
- **Your sign-in is protected the same way either way: sealed by the television's own key service once it has actually proven it can hand the sign-in back on a later launch, or kept in a file only this app can open.** The app now also tries a second, more stable way of identifying itself to that key service before falling back to the one it always used, which is why two different televisions can end up protected differently. A note in the repository compares this against how Netflix, Prime Video, Apple TV and YouTube protect the sign-in on the same kind of television: [docs/measurements/credential-storage-native-apps-2026-09-10.md](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/measurements/credential-storage-native-apps-2026-09-10.md).

## Compatibility

- **Plays video, verified by watching it — 2019 LG sets.** One television: an LG 49SM9000PLA, which reports platform release 4.10.2 (LG markets this generation as webOS 4.5).
- **Plays video, reported by someone else — one 2021 set.** [mariotaku](https://github.com/mariotaku) of webosbrew ran v0.2.1 on an LG 65UP7560AUD (platform release 6.5.2) on 2026-08-11 and got a picture: [issue #22](https://github.com/GLinnik21/plx-native/issues/22). Six of eight attempts played. That report has not been repeated on this version.
- **Starts, and nothing further is known — every other firmware from webOS 4.0 up.** The loader resolves this binary's libraries and symbols cleanly against every firmware image webosbrew has at 4.0 or newer. That grades startup and says nothing at all about whether video plays; the matrix is in the [technical audit](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/release-audits/v0.6.3.md).
- **Does not start — webOS 3.9.2 and older.** Symbols the app needs are missing from those firmwares, so the process is killed before anything appears.

## Known issues

- **Whether the real key service on a webOS 5-or-newer set behaves like the scripted one this release was tested against is still unconfirmed.** It reproduces the reporters' failure and the decompiled reason the sets differ, but no television with a real key service was available to check against directly. The next report from an affected set settles it.

## Help test this release

If you reported in [issue #76](https://github.com/GLinnik21/plx-native/issues/76): install this version, sign in once, switch the TV off and on, and say whether the account letter stays. If you ever see a screen offering "Try again" instead of your account, press it once and tell us whether it recovered. Keep error reports on; if anything about the stored sign-in still fails, the report now reaches us.

## Installing

Download **com.beb.plxnative_0.6.3_arm.ipk** and install it with the [Homebrew Channel](https://github.com/webosbrew/webos-homebrew-channel) or [dev-manager-desktop](https://github.com/webosbrew/dev-manager-desktop). You do **not** need a rooted TV.

Nothing in this distribution chain is signed, so this sha256 is what tells you the file you have is the file published here:

```
__IPK_SHA256__  com.beb.plxnative_0.6.3_arm.ipk
```

[Installing and checking a download](https://github.com/GLinnik21/plx-native/blob/main/docs/install-and-verify.md) covers the other assets, how to check the hash on each platform, and the Developer Mode expiry that uninstalls your apps. This package bundles FFmpeg under LGPL-2.1-or-later and its complete corresponding source is attached to this release. Exactly what was built, verified and shipped is in the [technical audit for v0.6.3](https://github.com/GLinnik21/plx-native/blob/release/v0.6/docs/release-audits/v0.6.3.md).
